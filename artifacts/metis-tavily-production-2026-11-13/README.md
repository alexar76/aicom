# METIS Tavily deployment, 13 November 2026

The production METIS service began using Tavily as the preferred provider for its existing `web_search` tool at 09:28:39 UTC. The overlay contains the four Tavily runtime modules from `d6a77ce9f` and the keyless fallback changes in `metis/exoskeleton.py` and `metis/tools/registry.py`. The deployed image is `sha256:8c4d597c6a8951a92490f1fc2ed68a28567d47dca79c5b9e1c0e386874416ee3`. The service uses the free, rate-limited Tavily API at `api.tavily.com`. Keyless Tavily falls back to the previous DuckDuckGo search on HTTP 429, HTTP 5xx or network failure. [Tavily keyless documentation](https://docs.tavily.com/documentation/keyless)

Before promotion, the production network reached Tavily without a key and received HTTP 200. A separate SSRF-pinned request in the candidate image returned five results. Its immediate successor received HTTP 429. The fallback returned five DuckDuckGo results both in the canary and in the promoted container, with separate forced-429 checks also returning five each. The forced check mocks the Tavily quota response and sends the fallback search over the live network.

The full local suite passed 457 tests. The isolated canary preserved all 143 knowledge entries, passed the auth regression checks and verified the prior auth module hashes. Production Docker health is healthy. Public `/health` returned 200 and `/v1/models` returned 200 with the existing authorized credentials and 401 for both missing and invalid credentials. The runtime parity check verified the environment addition `METIS_WEB_SEARCH_PROVIDER=tavily` and compared the other container settings, mounts, network memberships and host port configuration.
