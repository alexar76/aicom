# Один вызов клиента для цепочки с оплатой из кошелька

[English](one-call-pipelines.md) · [Русский](one-call-pipelines.ru.md) · [Español](one-call-pipelines.es.md) · [Français](one-call-pipelines.fr.md) · [中文](one-call-pipelines.zh.md)

`await run_pipeline(...)` объединяет подготовку, локальную подпись, исполнение корня и автоматическое ожидание в одну клиентскую операцию. Обычный путь содержит **два основных запроса к хабу**: подготовить граф и вызвать корень. Запросы к RPC блокчейна идут дополнительно. HTTP 202, потеря соединения или временные ошибки хаба могут потребовать повторных запросов к тому же заказу; ровно два HTTP-обмена не гарантируют завершение.

## Независимые продавцы и восстановление: 3.10.1

Платный граф теперь может включать доверенный peer, объявляющий **`SELLER-OP/1`**, без `SELLS_FOR`, аккаунта перепродажи и кредитного API-ключа этого peer. Покупатель оплачивает счёт продавца реальными средствами кошелька. Сохраняйте `source_hub` в каждом узле: существующие `run_pipeline(...)`, HTTP и MCP выбирают адаптер автоматически. Бесплатные цепочки по-прежнему работают без источника оплаты.

Предподготовка читает подписанный манифест peer и получает подписанное предложение у того же peer. Он должен быть активным и доверенным, с закреплёнными ключами; при закреплённом PQ-ключе обязательна и PQ-проверка. Адаптер проверяет SKU, покупателя, каталожную цену, указанный адрес продавца, сеть, токен, распределение сумм и срок. Произвольные URL из предложения не используются. Несовместимый peer отклоняется в preflight с `settlement_route_unsupported` до подписи и оплаты. Подготовка может оставить неиспользованный счёт продавца, но не исполняет работу и не переводит деньги.

Продавец создаёт постоянный `operation_id` и отдельный `operation_token`. Подписанное предложение содержит условия, nonce/срок счёта и схему входа. Токен хранится в закрытом состоянии запуска на хабе покупателя и не попадает в публичный счёт. Вход может зависеть от предыдущих шагов; конкретный вход, покупатель и хеш транзакции фиксируются при первом invoke. Изменение запроса возвращает HTTP 409. Секрет счёта остаётся у продавца: хаб покупателя не создаёт конкурирующий счёт и не передаёт кредитные ключи или SUB/1 grant. Закрытый ключ кошелька остаётся у клиента.

Три маршрута продавца: `POST /ai-market/v2/operations/prepare`, `POST /ai-market/v2/operations/{operation_id}/invoke`, `GET /ai-market/v2/operations/{operation_id}`. Invoke и status требуют `X-Operation-Token`; отсутствие или неверный токен даёт 404. Prepare принимает `product_id`, `capability_id`, `wallet`, `max_price_usd`; invoke — `input`, `wallet`, `tx_hash` (без хеша для бесплатной работы). Незавершённый invoke возвращает 202, завершённый успех или отказ — 200: проверяйте `status` и `success`. Status возвращает подписанный объект, не исполняет работу и не отправляет деньги. Это внутренний для сценария интерфейс продавца; клиент цепочки сохраняет два основных запроса к своему хабу.

После отправки исходной подписанной транзакции и проверки расчёта хаб покупателя сначала читает удалённую операцию. Продавец тоже проверяет оплату, сохраняет блокировку до вызова провайдера и кэширует подписанный исход. Подпись статуса связывает операцию с хешем предложения, хешем входа, кошельком и транзакцией. Потерянный HTTP-ответ восстанавливается чтением той же операции; сохранённый результат переживает перезапуск продавца. Итоговый счёт содержит `payment_rail: independent_seller`, подписанное предложение и статус/квитанцию. Локальный ребёнок SUB/1 связывает результат с корневым деревом, с финансированием `own`, без передачи кредитного allowance между хабами.

Воркер покупателя продлевает право исполнения каждые 30 секунд. Через 180 секунд без продления сохранённый незавершённый ребёнок `SELLER-OP/1` может быть продолжен тем же корневым invoke. Сервер атомарно передаёт право исполнения и блокирует запись устаревшего воркера. Read-only status объявляет `resume_same_run`, SDK сохраняет исходный платёжный пакет. Это не разблокирует произвольный старый провайдер. Для восстановления должны быть сохранены удалённый шаг и его job; остальные неопределённые состояния требуют сверки оператором.

Гарантия — **не более одной отправки провайдеру плюс долговечный результат**, а не универсальное «ровно одно исполнение». Конечный провайдер получает постоянные `Idempotency-Key` и `X-AIMarket-Operation-Id`; для закрытия собственного разрыва между работой и ответом ему нужна долговечная идемпотентность. Если продавец упал на этой границе или исход неизвестен, он сообщает `reconciliation_required` и не вызывает провайдера повторно. Зависшая блокировка продавца отмечается через 180 секунд, но не снимается. `recovery.action: contact_operator` означает сверку той же операции; `replacement_payment_allowed` остаётся false. Операции продавца пока обслуживают локальные листинги, исключая рекурсивный `pipeline.run@v1`; произвольный x402 endpoint автоматически совместимым не становится.

Нужен деплой хаба **3.10.1** и миграции БД **44** (операции продавца), **45** (права исполнения воркеров). Платёжные смарт-контракты передеплоивать не нужно. Независимым peer тоже нужно обновиться для публикации этого контракта продавца. В платном графе остаётся одна сеть/токен; готовый платный клиент поддерживает Base USDC и требует нативный газ. Спонсирование газа, другие сети, координация nonce между машинами и автоматические возвраты в этот релиз не входят.

Проверки охватывают отдельные ключи и БД двух хабов, неизменяемость запроса, подмену предложения, одновременные вызовы, потерю ответа, блокировку старого воркера, динамические входы, бесплатные цепочки и расчёты на локальном Anvil через настоящий платёжный код хаба. Два сценария Anvil используют одноразовый токен и тестовые кошельки, включая потерю ответа: это доказательство интеграции, а не обновления всех внешних продавцов. Проверки production фиксируются отдельно. Дополнительное списание в mainnet для этих проверок не требуется.

## 1. Подготовить граф

Вызовите `POST /studio/prepare-pipeline` с `nodes`, необязательным `wallet` и `max_budget_usd`. Endpoint объединяет прежние `/studio/preflight` и `/studio/paid-runs/{run_id}/prepare-pipeline`. Ответ содержит `ready`, `blockers`, идентификаторы шагов и условия оплаты, `total_units`, `run_id`, `access_token`, `graph_digest`, `wallet`, `expires_at` и `offers` с nonce счетов и авторизациями EIP-712. Подготовка не создаёт корневой job и не отправляет деньги. Бесплатному графу кошелёк не нужен, его `offers` пуст. Платный граф без кошелька отклоняется. Старые endpoints сохранены. Новый адрес опубликован в манифесте как `pipeline_execution.prepare_graph`.

`max_budget_usd` в запросе к хабу ограничивает только стоимость услуг. Параметр SDK `max_total_usd` дополнительно учитывает описанный ниже запас на сетевые комиссии.

```json
{
  "nodes": [
    {"id": "weather", "product_id": "gaia.gateway", "capability_id": "gaia.weather.read@v1", "source_hub": "https://iot.modelmarket.dev", "input": {"city": "Berlin"}},
    {"id": "air", "product_id": "gaia.gateway", "capability_id": "gaia.air.read@v1", "source_hub": "https://iot.modelmarket.dev", "input": {"city": "Berlin"}, "depends_on": ["weather"]}
  ],
  "wallet": "<buyer-address>",
  "max_budget_usd": 1
}
```

## 2. Подписать локально и исполнить

Клиент связывает ответ с запрошенным графом и кошельком, проверяет предложения и авторизации, балансы, сеть, ожидающие nonce и оценку газа. Локально подписывает авторизации EIP-3009 и транзакции EIP-1559, назначает последовательные nonce кошелька и сохраняет весь пакет до отправки. Хаб получает подписанные транзакции, но не закрытый ключ. Отправляется один корневой заказ `pipeline.run@v1`; исполнитель публикует платёж ребёнка только перед готовым к запуску шагом. Успешный ответ содержит итоговый результат, подписанный счёт, корневую квитанцию и дерево SUB/1. Проверяйте `status` и `success`: отказ поставщика тоже терминальный результат, а внешний платёж автоматически не возвращается.

```json
{
  "product_id": "hephaestus",
  "capability_id": "pipeline.run@v1",
  "source_hub": "local",
  "input": {
    "run_id": "<prepared-run-id>",
    "access_token": "<scoped-run-token>",
    "transactions": {"weather": "0x<signed-transaction>", "air": "0x<signed-transaction>"}
  }
}
```

## Python и командная строка

Установите выпущенный wheel с extra `client` (команда ниже). Клиент платит нативным **USDC в Base (8453) или Ethereum (1)** (см. дополнительные платёжные профили ниже) и проверен на macOS/Linux. Любая другая сеть или токен отклоняется, если их нет в вашей собственной политике `accepted_assets`. Бесплатному графу не нужны signer, RPC и потолок курса. Signer — локальный объект с `address`, `sign_message` и `sign_transaction`.

```python
import json, os
from eth_account import Account
from aimarket_hub.pipeline_client import run_pipeline

result = await run_pipeline(
    json.load(open("blueprint.json")),
    hub="https://modelmarket.dev",
    signer=Account.from_key(os.environ["PIPELINE_WALLET_KEY"]),
    rpc_url="https://mainnet.base.org",
    max_total_usd="1",
    state_path="order.private.json",
    wait=True,
)
print(result["status"], result["final_result"], result["bill_of_materials"])
```

```bash
python examples/pipeline-run/run.py blueprint.json \
  --hub https://modelmarket.dev --rpc https://mainnet.base.org \
  --max-total-usd 1 \
  --execute --prompt-key --state order.private.json
```

`--prompt-key` читает ключ локально без эха; альтернативно безопасно передайте `PIPELINE_WALLET_KEY` через окружение. Бесплатному графу и восстановлению после подписания ключ не нужен. Для нового CLI-заказа обязателен `--execute`. Прежний пример `client.py --budget` сохранён с прежним смыслом бюджета только на услуги. Для 3.10.1 нужен деплой хаба и миграции БД 44–45; платёжные смарт-контракты передеплоивать не нужно.

## Бюджет, состояние и восстановление

`max_total_usd` включает услуги и консервативный запас на газ. ETH/USD читается из закреплённого контракта Chainlink в Base через два RPC с разными именами хостов перед подписанием и каждой отправкой или повтором корневого вызова. Второй адрес по умолчанию — `https://base-rpc.publicnode.com` (либо `https://mainnet.base.org`, если основной — PublicNode); другой доверенный провайдер задаётся через `price_rpc_url` / `--price-rpc`. Обе проверки обязательны: chain ID Base, положительная завершённая котировка с 8 знаками и возрастом не более 1500 секунд, блок не старше 120 секунд и работающий sequencer после часового периода восстановления. Контракты читаются на номере проверяемого блока. Расхождение цен более 2% останавливает отправку. Для бюджета берётся большая цена **плюс 25%**. Старый необязательный `native_usd_ceiling` теперь служит дополнительной нижней границей расчётной оценки: может увеличить запас, но не уменьшить цену оракула и не заменить недоступный оракул. При ETH=$20 000 расчёт газа использует минимум $25 000, даже если в старом файле восстановления записано 6000.

На платёж резервируются 300 000 gas по удвоенной наблюдаемой цене и 100-кратная верхняя оценка L1 для 2048 байт из Base GasPriceOracle; дополнительно $0.05 на заказ. Превышение сохранённого бюджета приостанавливает отправку, сохраняя тот же заказ и подписи. Недоступная, устаревшая или противоречивая котировка также блокирует новые отправки; подстановки фиксированного курса нет. Бесплатным графам и локально сохранённым завершённым результатам оракул не нужен. После прерывания отправленного заказа сначала читается статус, затем при необходимости пересчитывается бюджет. В файле восстановления записаны обе котировки, раунды, время и применённая оценка. Остановка повтора из-за курса не повод создавать новую покупку вместо неизвестного результата старой.

Проверка происходит перед отправкой клиента, а не непрерывно во время исполнения длинного графа на хабе. RPC остаются доверенными источниками; разные имена хостов не доказывают независимость инфраструктуры. Курс USD и комиссия L1 могут измениться после отправки и не фиксируются подписью EIP-1559. Это консервативная защита бюджета, а не гарантированное долларовое эскроу.

[Chainlink ETH/USD — Base](https://data.chain.link/feeds/base/base/eth-usd) · [L2 sequencer](https://docs.chain.link/data-feeds/l2-sequencer-feeds).

Файл восстановления атомарно заменяется с правами 0600 и записывается через fsync; отдельная файловая блокировка исключает одновременное использование одного пути. В нём есть ограниченные учётные данные запуска и исполнимые подписанные транзакции — храните его приватно. Закрытого ключа в нём нет. После сохранения пакета resume не требует signer и не выбирает новые nonce или платежи. Если прерывание произошло до подписания, исходный signer ещё нужен. Потерянный ответ подготовки может оставить неиспользуемую котировку; платежа и корневого job на этом этапе нет. Не выполняйте параллельные транзакции с того же кошелька.

Ожидание включено по умолчанию. HTTP 202 продолжает тот же заказ; после транспортной ошибки клиент читает статус перед повтором исходного payload. `PipelinePending` сохраняет путь к состоянию при истечении времени ожидания или необходимости сверки. Занятая серверная запись опрашивается только чтением и не разблокируется клиентом. `wait=False` отдаёт ожидающий ответ для дальнейшего resume. Завершённый локальный файл возвращает сохранённый результат без сетевых запросов. Неуспешный ребёнок автоматически не вызывается и не оплачивается повторно. Для resume не передавайте граф и новые параметры бюджета/RPC: сохранённые граф и политика неизменны.

```python
result = await run_pipeline(resume=True, state_path="order.private.json")
```

```bash
python examples/pipeline-run/run.py --resume --state order.private.json
```

## Доступ внешних агентов: обновление 3.9.0

Клиент устанавливается из версионного wheel без клонирования репозитория. Подписанный манифест публикует `pipeline_execution.client.distribution`: URL и SHA-256. Пакет раздаёт хаб; это не означает, что эта версия уже опубликована в PyPI.

```bash
pip install "aimarket-hub[client] @ https://modelmarket.dev/clients/aimarket_hub-3.14.0-py3-none-any.whl"
aimarket-pipeline --help
```

Команда `aimarket-pipeline` принимает те же параметры, что пример `examples/pipeline-run/run.py`. Extra `client` включает подпись платежей и проверку ML-DSA. Нужен Python 3.11+. Проверены Linux/macOS; реализация блокировки Windows добавлена, но в этом релизе не проверялась. HTTP/MCP доступен из любого языка с локальным подписантом.

В MCP добавлены `pipeline_prepare`, `pipeline_invoke`, `pipeline_status`. Подготовка принимает граф, лимит услуг и необязательный адрес кошелька; исполнение — `run_id`, `access_token` и локально подписанный пакет; статус — только ID и токен. Бесплатному графу не нужны подписант и источник оплаты. Удалённый MCP-сервер не может подписывать за чужой кошелёк: для оплаты подключите локального подписанта либо Python-клиент. Закрытый ключ не передавайте аргументом инструмента. Полные подписи и платёжные предложения возвращаются без усечения.

SDK проверяет подпись подготовки, счёта и итоговой корневой квитанции, привязки к графу/заказу/кошельку, хеши результата и счёта, включая локальный кэш. Ключи хаба фиксируются при первой подготовке по HTTPS. Для независимой привязки доверия передайте `trusted_hub_key` и `trusted_hub_pq_key` (CLI: `--trusted-hub-key`, `--trusted-hub-pq-key`). После фиксации PQ-ключа удаление PQ-подписи отклоняется. Проверяется подписанный отчёт хаба, а не независимая идентичность каждого устройства.

`GET /studio/paid-runs/{run_id}/pipeline` с `X-Studio-Run-Token` читает результат без отправки денег и вызова детей. После потери ответа и при resume SDK сначала читает этот endpoint, затем при необходимости снова проверяет RPC/газ. Готовый заказ можно получить при недоступном RPC и выросших комиссиях. Занятое исполнение опрашивается только чтением. Повторы 429/5xx увеличивают интервал и учитывают числовой `Retry-After` в пределах оставшегося ожидания. `PipelineHTTPError` сохраняет `status_code`, `detail`, `state_path` для автоматизации.

Сохранённая резервация кошелька запрещает двум файлам состояния на одном хосте подписать пересекающиеся диапазоны nonce. Она хранится в `~/.aimarket/wallets`; общий каталог можно задать через `AIMARKET_WALLET_STATE_DIR`. Все участвующие клиенты должны использовать один каталог. Успех освобождает резервацию. После отказа она остаётся, пока все nonce не использованы либо авторизации не истекли и нет ожидающих транзакций. Сохраняйте исходный файл восстановления. Для разных хостов и стороннего ПО кошелька нужен общий подписант/координатор nonce либо отдельные кошельки: локальные файлы не координируют произвольных внешних подписантов.

Предпроверка возвращает стабильные `blockers[].code`: `settlement_route_unsupported`, `route_unavailable`, `mixed_assets_unsupported`, `service_budget_exceeded`. Внешние платные маршруты поддерживаются через хаб-продавца, настроенную перепродажу и независимые peer с SELLER-OP/1. Эта граница явно опубликована в манифесте. ## Оплата газа хабом — SDK 3.11.0

Новый режим SDK по умолчанию — `gas_mode="auto"`. Подписанный хабом ответ подготовки сообщает, доступна ли оплата газа для всего графа. Если доступна, покупатель локально подписывает только точные EIP-3009-разрешения на списание USDC. Отдельный кошелёк оператора подписывает сетевые транзакции и платит газ. Покупателю не нужны ETH, метод подписи транзакций и настройка RPC. `gas_mode="required"` отклоняет платный граф на подготовке, если спонсирование недоступно; `gas_mode="buyer"` сохраняет прежнюю оплату газа покупателем. У HTTP- и MCP-подготовки по умолчанию остаётся `buyer` для совместимости. CLI: `--gas-mode required`.

Подготовка возвращает `gas_sponsorship`; корневой вызов принимает `authorizations: {step_id: signature}` вместо `transactions`. Оба поля вместе запрещены. Котировка фиксирует режим оплаты, покупателя, получателей, суммы, nonce разрешений и сроки. При повторе нельзя заменить подписанный пакет. Закрытый ключ покупателя хабу не передаётся. Подписанный счёт содержит режим спонсирования и плательщика газа каждого платежа; комиссия за газ для покупателя равна нулю. Бесплатные графы по-прежнему не требуют ни подписанта, ни спонсора, даже с `required`.

Первый вариант поддерживает прямые платежи USDC в Base 8453, включая совместимых сторонних продавцов. Текущий MarketSplitter связывает плательщика с `msg.sender`, поэтому платежи с разделением комиссии явно исключены. Для прямого маршрута передеплой контрактов не нужен. `auto` может перейти к газу за счёт покупателя; `required` — не может. Пустой кошелёк спонсора, исчерпанный суточный лимит, недоступный оракул или занятый nonce оставляют заказ в ожидании для продолжения без нового платежа.

Перед каждым новым платежом хаб проверяет живой оракул ETH/USD, консервативную оценку газа, баланс спонсора и лимиты на платёж/сутки. Только после разрешения ссылок и проверки входа шага он атомарно резервирует nonce и сохраняет подписанные байты в общей БД. У кошелька спонсора одновременно допускается одна неподтверждённая транзакция. Несколько воркеров используют общий учёт nonce и бюджета; повтор отправляет те же байты. Сбой после сохранения транзакции восстанавливается даже после истечения котировки: перевод мог уже состояться. Готовый сохранённый результат не требует RPC. Разные БД релееров не должны использовать один газовый кошелёк.

Настройки оператора: `AIMARKET_PIPELINE_RELAY_ENABLED=1`, `AIMARKET_PIPELINE_RELAY_KEY_FILE` (закрытый файл, не симлинк), `AIMARKET_PIPELINE_RELAY_RPC`, необязательный `AIMARKET_PIPELINE_RELAY_PRICE_RPC`, `AIMARKET_PIPELINE_RELAY_DAILY_WEI` (по умолчанию 20000000000000) и `AIMARKET_PIPELINE_RELAY_MAX_GAS_USD` (0.10). Пополняется отдельный газовый кошелёк; ключ покупателя на сервере не устанавливается. За сутки резервируются консервативные верхние оценки комиссии в ETH; разница после майнинга не освобождается. Долларовая оценка — проверка с запасом, а не неизменяемый on-chain-лимит в USD. Уже сохранённые транзакции можно восстановить при отключённом создании новых спонсируемых платежей.

## Восстановление результата провайдера — SDK/Hub 3.12.0

`PROVIDER-OP/1` закрывает разрыв, когда провайдер завершил работу, а его ответ не дошёл до хаба продавца. Совместимый провайдер до исполнения записывает ID операции и хеш продукта, capability и входа. Перед ответом он сохраняет результат и подпись. Повтор той же операции возвращает сохранённый результат; другой вход отклоняется. Параллельные запросы не запускают работу дважды. KOVA ведёт этот журнал в своей существующей SQLite-базе.

Продавец явно включает совместимые продукты: `AIMARKET_PROVIDER_OPERATION_PRODUCTS=kova-network`. Новые подписанные офферы `SELLER-OP/1` объявляют `provider_recovery: PROVIDER-OP/1`; исходные URL и публичный ключ провайдера фиксируются в закрытом состоянии операции. После потерянного ответа или зависшего исполнения продавец читает `GET <invoke_url>/operations/<operation_id>`. Проверяются подпись, ID операции, продукт, capability, хеш точного входа и отдельная подпись результата. Для платной работы требуется сохранённая проверка исходного платежа. Завершённый ответ продавца неизменяем, даже если старый воркер позже вернулся. Восстановление не отправляет второй POST провайдеру и не создаёт новый платёж.

Входы invoke и status у KOVA требуют одного закрытого межсервисного токена. Настраиваются совпадающие `AIMARKET_CAPABILITY_TOKEN` и `KOVA_CAPABILITY_TOKEN`; в `AIMARKET_INVOKE_HOST_GATEWAY` разрешается только хост провайдера оператора. Ключи и токены операций не публикуются в доказательствах. Покупатель продолжает обращаться через платёжные проверки хаба.

Это восстановление при поддержке провайдера, а не обещание однократных побочных эффектов у любого чужого сервиса. Если провайдер упал между внешним действием и сохранением результата, исход остаётся неизвестным; автоматического повторного исполнения нет. Провайдер должен связать бизнес-транзакцию с ID операции либо проверить действие перед записью результата. Старые провайдеры сохраняют ручное разрешение неопределённости. Неизвестные записи KOVA блокируют повтор, защищая от дублирования изменений.

Уже оплаченный счёт можно предъявить после истечения срока, если подтверждённое время блока строго раньше срока. Поздняя оплата отклоняется; одноразовое использование nonce сохраняется. Явный список RPC через запятую теперь разбирается как список без добавления внешних запасных узлов. В публичном счёте pipeline убрано внутреннее поле гранта job.

## Возврат с согласия продавца — SDK/Hub 3.13.0

Подтверждённый прямой платёж Base USDC можно вернуть через `SELLER-REFUND/1`. Покупатель запрашивает предложение возврата для шага завершённой цепочки; исходный продавец одобряет его локальной подписью EIP-3009. Газ оплачивает спонсор. Приватные ключи хабу не передаются; ETH у покупателя и продавца для этого пути не требуется. Подготовка предложения не переводит деньги и не обязывает продавца вернуть оплату.

HTTP использует исходный `X-Studio-Run-Token`: `POST /studio/paid-runs/{run_id}/refunds/{step_id}/prepare` создаёт или возвращает подписанное предложение; `POST /studio/paid-runs/{run_id}/refunds/{step_id}` принимает `{"authorization":"0x…"}` и продолжает тот же возврат; `GET` по этому пути читает статус. HTTP 202 означает ожидание. MCP предоставляет `pipeline_refund_prepare`, `pipeline_refund`, `pipeline_refund_status` с теми же run ID, scoped access token и step ID. Передавайте только подпись продавца, никогда ключ кошелька.

SDK `refund_pipeline(state_path=..., step_id=...)` возвращает предложение без оплаты. Продавцу передаётся только объект `offer`, а не приватный файл восстановления покупателя. Продавец вызывает `sign_refund_offer(offer, seller_signer=..., buyer_wallet=..., original_tx_hash=..., max_usdc=..., trusted_hub_key=..., trusted_hub_pq_key=...)` из `aimarket_hub.refund_client`. Получатель, исходный платёж, потолок суммы, токен, сеть и подпись хаба проверяются локально. Покупатель отправляет полученную подпись через `refund_pipeline(..., authorization=signature)`. Повтор с тем же приватным файлом продолжает тот же возврат; `RefundPending` сохраняет его идентичность. Решение о праве на возврат приложение продавца принимает до подписи.

Хаб допускает только исходного продавца, исходного покупателя и полную точную сумму проверенного платежа. Цепочка должна иметь статус completed или failed: неизвестный результат провайдера сначала нужно сверить. Подпись после отправки неизменна. Байты транзакции сохраняются до трансляции; используется общий координатор nonce и бюджета спонсора в БД. Потеря ответа и перезапуск продолжают ту же транзакцию. Просроченное разрешение обновляется только до подписания транзакции хабом, с прежними refund ID и nonce авторизации: старое и новое разрешения не могут выполнить два перевода.

Исходный подписанный счёт и результат неизменны. Отдельная подписанная корректировка `pipeline.refund/1` связывает хеши исходного платежа и возврата, сумму, токен, сеть, стороны и плательщика газа. Чтение статуса не переводит деньги. Первая версия поддерживает один полный возврат прямого Base USDC платежа без split-комиссии при доступном спонсоре. Частичные возвраты, возврат комиссий MarketSplitter, принудительное списание и произвольные токены пока не реализованы. Продавец может отказать или не иметь средств; недостаток бюджета спонсора оставляет тот же возврат в ожидании. Уже потраченный газ не возвращается. Бесплатные цепочки по-прежнему работают без источника оплаты.

## Дополнительные платёжные профили и несколько машин — SDK/Hub 3.14.0

SDK теперь принимает нативный USDC в **Base 8453 и Ethereum 1**: адреса закреплены, decimals=6, EIP-712 `USD Coin` / `2`. Один платный граф по-прежнему использует одну сеть и один актив; смешанные графы нужно разделять на отдельные заказы. Хаб должен предложить соответствующий способ оплаты: поддержка сети в SDK не переносит баланс между сетями и не меняет валюту продавца. Бесплатные графы работают как прежде. Спонсирование газа и возврат с согласия продавца пока поддерживают прямые платежи Base USDC; в Ethereum газ оплачивает покупатель. `gas_mode="required"` отклоняет платный маршрут без спонсора до подписи.

`accepted_assets=[...]` заменяет стандартный список SDK. Каждая запись явно задаёт `chain_id`, `token_contract`, `decimals`, `eip712_name`, `eip712_version`, `usd_pegged: true`, `authorization: "EIP-3009"`. Это политика покупателя для проверенного долларового токена, а не доказательство таких свойств у любого ERC-20. Хаб не может дописать туда свой актив. Суммы рассчитываются десятичной арифметикой без ошибок float. Недолларовые активы, обычные ERC-20 только с approve, другие сети и атомарные межсетевые графы не конвертируются молча, а отклоняются. CLI: `--accepted-assets approved-assets.json`. Политика сохраняется в файле восстановления и не меняется при resume.

Для локальных продавцов Ethereum задайте `AIMARKET_X402_CHAIN=ethereum`. Проверка и отправка платежа используют подписанный chain ID; `AIMARKET_SETTLE_RPC_1` и `AIMARKET_SETTLE_RPC_8453` задают отдельные RPC. Общий `AIMARKET_SETTLE_RPC_URL` остаётся исключительным резервным списком: RPC только Base нельзя использовать для обслуживания Ethereum. Перед проверкой receipt и трансляцией RPC обязан показать сеть счёта. Пользовательскому активу хаба также нужны правильные `AIMARKET_X402_ASSET`, `AIMARKET_X402_ASSET_SYMBOL`, decimals, `AIMARKET_X402_EIP712_NAME`, `AIMARKET_X402_EIP712_VERSION` и совпадающий список покупателя. Недолларовый токен нельзя считать долларом.

Газ Ethereum оценивается по свежему ETH/USD через два разных RPC-хоста с запасом цены 25%, ограничением газа транзакции и прежним резервом $0,05. Дополнительной Base L1-комиссии в Ethereum нет. Закреплён Chainlink feed `0x5f4eC3Df9cbd43714FE2740f5E3616155c5b8419`: 8 decimals, heartbeat 3600 секунд, допустимый возраст 3900 секунд. Base сохраняет проверку sequencer и отдельный L1-резерв. Неверная сеть, старые блоки или цены и расхождение выше 2% останавливают оплату. Ручной курс может только поднять потолок.

Для агентов на нескольких машинах установите extra `postgres` и задайте один **принадлежащий покупателю** `AIMARKET_WALLET_DATABASE_URL` до создания заказов. Нужны прямое соединение PostgreSQL или session pooling; transaction pooling PgBouncer не сохраняет session advisory locks. Координатор сериализует каждую пару `(chain_id, wallet)` между соединениями. До отправки БД сохраняет приватное состояние восстановления, scoped token хаба и точный подписанный набор транзакций; приватный ключ кошелька в неё не записывается. Доступ к БД — только сотрудничающим агентам покупателя. DSN не сохраняется в заказе и не отправляется хабу.

Чтобы перенести незаконченный заказ, безопасно скопируйте его приватный файл на другую машину и вызовите `run_pipeline(resume=True, state_path=...)`. Устаревшая копия до подписи загрузит сохранённый набор из PostgreSQL; завершённый результат читается до новой подписи. Другой заказ не заберёт незавершённую резервацию. После терминальной ошибки она освобождается только при использовании всех подписанных nonce либо после истечения авторизаций, если нет ожидающих транзакций. Недоступность БД останавливает новую отправку; завершённый локальный результат доступен. Все агенты должны использовать одну БД и схему; нельзя смешивать независимые координаторы или посторонний софт для того же кошелька. По умолчанию остаются локальные файлы; покупателю со спонсируемым газом PostgreSQL не требуется.

Проверка выполнена на настоящем временном PostgreSQL: независимые соединения, сбой процесса, устаревшие копии, ошибка сохранения и отсутствие повторной подписи. Локальная EVM с chain ID 1 выполнила настоящий SDK-платёж EIP-3009; oracle проверяется отдельно, поскольку локальная сеть не содержит Chainlink. В mainnet Ethereum выполнены только чтения: два RPC согласились по курсу, а name/version/decimals USDC совпали с профилем. Покупку в mainnet Ethereum не заявляем; дополнительных денег не потрачено.
