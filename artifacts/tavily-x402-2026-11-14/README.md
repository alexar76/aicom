# Tavily Advanced Search x402 verification, 14 November 2026

Tavily quotes 10,000 atoms (0.01 USDC) on Base mainnet for `POST https://x402.tavily.com/search`. A new unpaid challenge may supply a different `payTo`. It also offers `aws:base`; ARGUS selected only `eip155:8453` with the native Base USDC contract. [Tavily x402 contract](https://docs.tavily.com/documentation/machine-payments/x402)

On 13 November, two ARGUS attempts and one using Tavily’s documented client flow returned HTTP 402 after authorization. The latter two included `Verification error`. All three authorizations expired unused on Base. The payer held 0.838158 USDC throughout those checks. [Prior HTTP and chain evidence](../x402-integrations-production-2026-11-13/README.md)

On 14 November, the live-quote check used a newly generated, unfunded key and intercepted the signed request before transport. The payload matched the live offer’s resource, token, recipient, amount and time limit. EIP-712 recovery returned the signer, and the computed domain separator matched `DOMAIN_SEPARATOR()` on Base USDC. Tavily’s response clock and the Base block timestamp differed by two seconds; the local clock was ahead by 3,473 seconds and was corrected for this check. No signed request left the process. [Sanitized evidence](dry-check.json) · [Reproducible probe](dry-check.mts)

This confirms the adapter can construct a valid authorization from a fresh offer. It does not identify why Tavily’s payment verifier rejected the previous calls. The `bazaar` extension appeared in the offer; the ARGUS adapter did not echo it in the signed envelope. The previous SDK-wrapper attempt still returned `Verification error`, so there is no evidence that adding the extension fixes the rejection. The paid tool remains disabled in the private Telegram bot. METIS’s keyless search uses a separate endpoint and is not evidence of x402 payment.

The follow-up probe, [one-payment.mts](one-payment.mts), checks the earlier nonces and the pilot wallet balance using read-only RPC calls by default. A funded, authorized run with `--one-payment` uses Tavily’s minimal request and SDK flow, sends at most one authorization, then checks for both search links and the exact Base transfer. The exclusive attempt file prevents a second launch from resubmitting. A timeout or an ambiguous response requires reconciliation of that nonce after expiry before any new attempt. At the recorded check the pilot wallet had 8,158 atoms, 1,842 short of the quoted amount.

After the wallet was funded to 6.779115 USDC, the probe sent one 0.01 USDC authorization at 14:51:59 UTC. Tavily responded with HTTP 402 and `Verification error` again. The response had no payment receipt or search results. Base block 57,388,035 was past the authorization deadline and showed the nonce unused, no matching authorization event, and the same wallet balance. The test rules out an insufficient USDC balance as the cause of this rejection. Tavily’s payment verifier would need to provide the specific error to pinpoint it.
