Abstract
The Model Context Protocol (MCP) connects LLM agents to external tools, and public
registries now list tens of thousands of MCP servers. Most empirical studies of this ecosys-
tem arestatic. None calls the tools of registry servers at scale to check whether the servers
start and follow the protocol. This paper does. From the official registry (17,432 unique
servers) we run a complete census of all 6,106 self-contained, locally-installable servers,
each launched in an isolated sandbox. A conformance harness then sends each one an
unknown tool name, an argument of the wrong type and a malformed protocol frame. Only
63.5% (95% CI 59.9–66.5) of installable servers start and complete a handshake. Of those
that respond, 88.4% (95% CI 86.6–90.0) report an unknown tool differently from the spec-
ification’s illustration. Another 3.5% (95% CI 2.8–4.2) run a tool on an argument their own
declared schema rejects and return an ordinary result, although the specification requires
servers to validate all tool inputs; asked for top stories with a limit of"not-a-number",
one returned an empty feed. Both behaviors trace to SDK defaults rather than to server
authors. A re-run sixty-nine days later shows how far that dependence reaches: a breaking
release of the official Python SDK, published nine days after our snapshot, stopped 58%
of the Python-SDK servers that had worked, and pinning the SDK below it restores them.
Conformance among the servers that still ran did not change. We release the harness and
the disclosure-filtered dataset.

1 Introduction
Large language model agents act through external tools, and the Model Context Protocol
(MCP) is the dominant standard for connecting them. In under two years MCP went from one
vendor’s proposal to an ecosystem whose public registries list tens of thousands of servers.
One of them, the official registry, contains 17,432 unique servers at the time of our study.
When a server fails to start, accepts ill-typed arguments or returns a malformed result, the
agent calling it can act on wrong output without knowing it. Every agent built on MCP inherits
the reliability of this server layer.
Most published empirical studies of the MCP ecosystem examine serverswithout running
them, and those that do run them look for vulnerabilities. Existing work scans source code
and metadata for health and maintainability, crawls registries to characterize scale and supply-
chain structure, or mines GitHub issues to build fault taxonomies. None of it answers a simpler
question:if you install these servers and speak the protocol to them, do they start and do
they follow the specification?The protocol’s own conformance test suite is built for SDK
maintainers to run in continuous integration, and we know of no use of it on the deployed
ecosystem. It exercises the SDKs, and the 17,432 servers published on top of them go untested.
We ran that measurement. Starting from the official registry, we census every self-
contained, locally-installable server, launch each in an isolated sandbox, and drive it through
a conformance harness. The harness exercises the initialization lifecycle, tool listing and
declared-schema validity. It then sends three inputs that come up in ordinary agent sessions:
a call to an unknown tool, a call with a wrong-typed argument, and a malformed protocol
frame. Every check tests behavior that all observed revisions describe in the same terms, and
the version each server negotiates is recorded with its result. Requirements stated with an
RFC-2119 keyword (MUST/SHOULD) are graded apart from behavior the specification only
shows in an example.
Only 63.5% (95% CI 59.9–66.5) of installable servers get as far as a completed protocol
handshake. The rest fail in ways we classify into a startup-failure taxonomy, from install errors
to silent exits to hangs. Among servers that do respond, 88.4% (95% CI 86.6–90.0) report a
call to a non-existent tool as a “successful” tool-execution error (isError: true) instead
of the JSON-RPC protocol error the specification illustrates. We trace this divergence to the
default behavior of the official SDKs, which is inherited by the servers built on them. An open
proposal would reclassify unknown-tool failures to match what the SDKs already do (Model
Context Protocol contributors 2026), and our census measures how much of the ecosystem
already behaves that way. Separately, 3.5% (95% CI 2.8–4.2) of responding servers run a tool
on input that violates the schema they publish, and return a well-formed result. Asked for the
top stories on Hacker News with a limit of"not-a-number", one returned an empty feed.
An agent reads that as there being no stories, and nothing in the reply marks it as an error.
The specification requires servers to validate all tool inputs. A further 0.5% (95% CI 0.3–0.7)
fail to recover from a malformed frame and answer nothing further, although JSON-RPC 2.0
requires a reply to every request.
We then re-ran the same frame on 26 September 2026. The servers were launched at the
same versions with the same commands, and 617 that had answered in July no longer did.
Most of the loss has one cause. The official Python SDK published a breaking major release
nine days after our snapshot, servers that declared the dependency as a range resolved to it,
and they no longer start: 58% (95% CI 55–61) of the Python-SDK servers that worked in July.

Pinning the SDK below the new release restores them. Conformance among the servers that
still start did not move.
We organize the study around five research questions:
• RQ1 (Runnability).What fraction of registry-published servers can a client install and
start, and when they do not start, why not?
• RQ2 (Lifecycle conformance).Of the servers that respond, how many implement the
initialization lifecycle correctly, list their tools and publish valid schemas?
• RQ3 (Input enforcement).How many servers run a tool whose declared schema rejects
the argument it was given, and what does the client receive when they do?
• RQ4 (Specification versus practice).Where the specification and deployed behavior dis-
agree on error reporting, how large is the divergence, what causes it, and which side is
moving?
• RQ5 (Correlates).Do runnability and conformance vary with the package registry a server
ships on?
This paper makes five contributions:
• A protocol-level conformance measurement of the MCP ecosystem by execution(C1):
prior ecosystem studies read code and metadata. We install every eligible server in the
registry, speak the protocol to it, and test how it responds to inputs.
• A taxonomy(C2) of why installable servers fail to start, and of what a server that fails to
reject a bad argument returns to the client.
• A root-cause account of the spec–practice divergence(C3): by attributing each server to
its SDK, we show that the dominant divergence comes from defaults in the official SDKs.
• Open infrastructure(C4): a conformance harness whose checks align with the official
suite’s categories and that runs against any deployed stdio server, with a test suite, and the
released measurement dataset. Others can repeat the census, and authors can check their
own servers.
• A dated natural experiment(C5): re-running the same frame isolates a single SDK release
that stopped more than half of the Python-SDK servers that had worked, confirmed by
reversing it.
2 Background and Related Work
2.1 The Model Context Protocol
MCP standardizes how LLM agents discover and invoke external tools. A client and server
negotiate a protocol version and capabilities during aninitializehandshake. The client can
then list tools (tools/list) and invoke them (tools/call). Messages follow JSON-RPC
2.0, including its error-object semantics and its reserved error codes. Most deployments run
the server locally over stdio, and on that transport stdout carries protocol traffic and nothing
else. The specification is versioned by date, and servers may negotiate down to a version they
support.
3
2.2 Static studies of the MCP ecosystem
The ecosystem has been studied at scale but rarely by running it, and the peer-reviewed
studies of it are static. One analyzes source and metadata for roughly 1,900 GitHub-sourced
servers with static scanners and code-smell detectors (Hasan et al. 2026). Another surveys
the protocol’s ecosystem and its security threats (Hou et al. 2026). A third examines 67,057
servers across six registries and finds registry weaknesses that allow a server’s identity to be
hijacked, again by static analysis (Li and Gao 2026). Ours differs on both axes: the population
comes from the official registry a client resolves against, and every server is executed.
Registry measurement elsewhere crawls several marketplaces and characterizes scale,
maintenance and supply-chain concentration across some 8,000 servers, using marketplace
data without running any of them (Guo et al. 2025). A companion dataset effort catalogues
3,238 candidate MCP repositories on GitHub and classifies them by operational role, again
from repository evidence (Toeppe et al. 2026), and a parallel line studies theapplication
side, characterizing how 1,723 MCP applications configure and supervise the servers they
consume (Majeed et al. 2026). A census of the registry’s version history finds that 51.1% of
servers with more than one version changed what they advertise between versions, most of
them without notice, and that such drift predicts security findings (Kraishan 2026); it reads
each version’s metadata and source and runs none of them. Fault taxonomies take another
route and mine GitHub issues (Owotogbe et al. 2026; Taraghi et al. 2026). One finds tool
faults and data-schema faults the two most frequent categories (Owotogbe et al. 2026), the
same two areas our harness tests. None of this work executes a server.
2.3 Execution-based work is security-focused
Some prior work does execute MCP servers, to find security problems. Sandboxed behavioral
scanners hunt vulnerabilities in curated corpora (Tan et al. 2026), and taint-style analyzers
confirm exploitable flaws across tens of thousands of repositories (Sun et al. 2026). A security-
invariants benchmark avoids live third-party execution altogether in favor of fixtures and a
40-repository metadata sample (Liu 2026). Malicious-server detection, authentication studies
and dynamic assessment of internet-facing endpoints all keep to security questions (Huang
et al. 2026; Zhou et al. 2026; Padilla 2026).
MCPZoo assembles 64,611 unique servers, of which more than 37,288 support dynamic
analysis, and uses them to show that existing security scanners are unreliable, with fewer than
half of sampled alerts holding up under manual validation (Chen et al. 2026). That corpus
differs from ours in two ways. First, MCPZoo is built byrepairingservers: a multi-agent
framework infers environments and iteratively fixes deployment and runtime defects until
in-the-wild repositories become running services. That construction is the right choice for
studying what a server does once it runs, and it necessarily removes the signal we measure:
how often a server runs when a client installs it as published. Second, its population is collected
from multiple public markets, and ours is the official registry, the index a client installs
from. That their corpus needed a repair framework fits our runnability finding. Conformance
is a separate question: whether a server that is neither malicious nor vulnerable does what
the specification says. Concurrently with our work, Afsar draws a seeded random sample of
400 npm stdio servers from the same registry and probes each without repair. There 48.8%
complete a handshake, servers that never start (37.5%) outnumber those missing credentials
4
(13.3%), and the 195 that run show no fatal schema violations across 2,766 tools (Afsar 2026).
That study samples one package ecosystem and checks declared structure. We census both
npm and PyPI and test behavior, calling tools with inputs the server should reject.
2.4 The specification’s own error-handling debate
The categorization this paper measures is under active revision. SEP-1303, accepted and
reflected in the current specification, moved tool input validation errors out of protocol errors
and into tool execution errors, reasoning that a language model can self-correct only from
an error that reaches its context (Model Context Protocol contributors 2025). SEP-2145, still
open, extends the same treatment to tool resolution failures including unknown tools. Its stated
purpose is alignment with what the Python and TypeScript SDKs already do (Model Context
Protocol contributors 2026). We take no position on which mechanism is correct. We measure
what fraction of the deployed ecosystem the proposed alignment already describes. Concurrent
with this work, a practitioner census posted to the same proposal probed roughly 10,500
remoteregistry endpoints and harvested their tool lists. It reports that 88.8% of mutating tools
declare no output schema, and argues that the proposal’s output-validation clause is inert for
most of the write path (siliroid 2026). That measurement and ours are close to disjoint: it
probes hosted HTTP endpoints and reads declared metadata while we install and execute local
stdio servers and test behavior against inputs. It addresses the output-validation clause, and
our checks cover tool resolution and input enforcement.
2.5 Conformance tooling and the gap we fill
The protocol maintainers ship a conformance suite for client and server implementations,
aimed at SDK authors running it in continuous integration. To our knowledge it has not been
used to measure the deployed ecosystem. As far as we know, ours is the first reproducible
conformance measurement of this ecosystem that installs and executes the published servers
and tests their behavior against adversarial inputs with an open harness and dataset.
3 Methodology
We measure the MCP server ecosystem byexecutingit. This section defines the sampling
frame, the conformance harness, the sandbox, and the grading rules (Figure 1). The harness
and the released dataset make every number reproducible.
3.1 Sampling frame
We crawl the official MCP registry (registry.modelcontextprotocol.io) via its cursor-
paginated API, retaining the latest published version of each server, which yields 17,432
unique servers. Each server declares zero or morepackages(installable artifacts on npm, PyPI,
OCI, NuGet, or Cargo) and/orremotes(hosted HTTP endpoints). Our study population is the
set of servers that are (i) locally installable, (ii) use thestdiotransport, (iii) distributed on
npm or PyPI (the two dominant registries), and (iv)self-contained: they declare no required
environment variable or argument that lacks a default. Criterion (iv) restricts us to servers that
a client could launch without provisioning secrets, which limits what mass execution can do
to third-party systems and keeps the population reproducible.

each decision follows from its fields. The script and the sample are released.
3.2 Conformance harness
The harness,mcpprobe, is a minimal, hand-written JSON-RPC client speaking line-delimited
messages over the server’s stdio. We do not use an official SDK client. To observe raw behavior,
including responses to malformed frames, the probe must not inherit any SDK-side correction
or validation. The harness offers protocol version2025-06-18at initialization (the then-
current revision was2025-11-25), records the version the servernegotiates, and records it
with every result. A server that supports the offered version must answer with it, and 3,576 of
3,685 responders did. The rest negotiated three other revisions: 104 settled on an older one, the
oldest dating to 2024-11-05, and 5 answered with a revision newer than the one offered, which
the lifecycle does not permit. Our checks encode requirements that every one of these revisions
states in the same terms, so no verdict depends on the negotiated version. A requirement that
moved between revisions would need a version-dependent rule, and we add none.
Each server is driven through the following checks, whose identifiers align with the
categories of the officialmodelcontextprotocol/conformancesuite where an analogue
exists:
• server-initialize: theinitializerequest must return a result carrying a protocol version
and a capabilities object, after which the harness sendsnotifications/initialized.
• ping: apingmust return an empty-object result.
6
• tools-list: if the server advertises the tools capability,tools/listmust return an array in
which every entry has anameand aninputSchemaobject.
• tools-schema-valid: each declaredinputSchemamust be a valid JSON Schema (checked
by meta-validation).
• tools-call-unknown: calling a non-existent tool must be rejected. The specification’s Error
Handling section categorizes “Unknown tools” underProtocol Errors(standard JSON-
RPC errors) and illustrates this with a-32602example, as opposed toTool Execution
Errorsreported as a result withisError: true. This categorization is prose plus an
example, and it uses no RFC-2119MUST/SHOULDkeyword. A diverging response is never
scored as a “violation”. Each server’s choice between the two mechanisms is recorded (see
error-as-resultbelow).
• tools-call-invalid-args: for the first listed tool with a typed property, calling it with a value
of the wrong type should be rejected. The harness poisons the first typed required property
when the schema declares required properties, and the first typed property when it declares
none; in the September run, where this was recorded, the poisoned property was optional
in 29% of calls. A schema-declared type binds whether or not the property is required. The
spec is ambiguous here, since it lists “Invalid arguments” under Protocol Errors but “Invalid
input data” under Tool Execution Errors. We counteithera protocol errororanisError
result as acceptable, and flag only a plain success response (the tool ran on ill-typed input)
as a defect.
• malformed-json: after receiving a syntactically invalid frame, the server must not crash or
hang, and a subsequentpingmust still succeed.
• stdout-purity: under the stdio transport, the server must emit only protocol messages on
stdout, and any non-JSON line is a channel-corruption defect.
3.3 Grading and the error-as-result category
Verdicts arepass,fail,warn,skip, and one category introduced by calibration:error-as-
result. When validating the harness against the official reference servers (server-memory,
server-everything), we found they answer an unknown-tool call not with the specified
JSON-RPC-32602error but with asuccessfulresponse whoseresult.isErrorflag is set.
Because this behavior originates in the official SDKs, it reaches most of the ecosystem, and it
earns its own verdict category. Its prevalence is a result in its own right.
3.4 Sandbox
Each server runs in a fresh container (node:22-slimfor npm, anastral-sh/uvimage for
PyPI) with a memory cap, a single CPU, a PID limit,no-new-privileges, all Linux capa-
bilities dropped, and no host filesystem mounts. The harness supports two probe conditions.
In thetwo-phasecondition, an online install pass populates the cache and the conformance
probe then runs with--network=none, so no server code has network access while it is being
measured. In thesingle-phasecondition the network is available throughout, and install and
probe occur together in one ephemeral container. The census reported here was measured in
the single-phase condition, for the operational reasons given in Section 3.5, and Section 7
carries the consequences for validity.
7
3.5 Execution environment and probe condition
The census was executed on a single disposable cloud instance (no cloud credentials attached)
using the online single-phase condition: install and probe occur in one ephemeral--rm
container per server, with nothing cached between servers, which keeps disk usage bounded
across the full ecosystem. The recorded launch command of every run confirms that no volume
was mounted. We did not run a controlled comparison of the two conditions. In development
runs on smaller subsets we saw the same error-as-result prevalence and the same silent type
non-enforcement among responding servers under both. Handshake yields from those runs
are not comparable, because the subsets differed.
Two groups of runs ended for reasons outside the server’s control. 32 probes (0.5%) were
killed with exit 137 by either the memory cap or an automated guard that reclaims host disk
space, and the census does not record which. Another 17 (0.3%) aborted on a harness-side
error before any check ran. Only one of these 49 runs had completed a handshake first, and
the rest can only lower the reported yield.
3.6 SDK-level confirmation
Where a conformance failure concentrates in one SDK family, the census cannot say whether
the library permits the failure or the authors introduced it independently. For the input-
validation result we probed the SDK on its own. We build two minimal servers, each exposing
one tool that declares a single required string property. One uses the low-levelServerAPI and
the other the high-levelMcpServerAPI, both on the same SDK release. Each is driven with
the harness check used in the census: atools/callcarrying an integer where the declared
schema requires a string. The construction is otherwise identical, so any difference in outcome
is a property of the API path. We report the result in Section 4.3, and the two servers and the
probe script are released with the harness.
3.7 Funnel accounting
RQ1 asks whether a server runs, and we count every stage: declared→eligible (self-
contained stdio npm/PyPI)→container started→process launched→handshake completed
→probed. Servers that never complete a handshake are classified into startup-failure cate-
gories (Section 4) from their exit code and stderr, which accounts for the lost yield. Runs
broken by the harness are a separate outcome, reported with the funnel and excluded from the
graded population, because they measure our instrument.

4 Results
We launched all 6,106 servers in the eligible frame, and on 17 of them our own probe failed
on a broken pipe or an uncaught exception, leaving those runs with no verdict about the server.
We report them with the funnel and exclude them from every denominator, which leaves 6,089
graded servers.
4.1 RQ1: Runnability and the startup funnel
Once two launcher artifacts are corrected, the entry-point problem described in Section 4.5
and the launch arguments described in Section 7, 3,864 of 6,089 servers complete the MCP
handshake, a rate of 63.5% (95% CI 59.9–66.5), against an uncorrected census figure of 60.5%
(95% CI 56.2–64.0). Roughly two in five never serve the protocol, and Figure 2 classifies
those failures by cause.
Servers that only need credentials or configuration are counted apart from servers that
crash, since a missing setting is a documentation gap. Most failures happenaftera successful
install: the package downloads, then the process crashes, hangs, or exits without speaking the
protocol. The software fails after the packaging has done its job. A concurrent random draw
of 400 npm servers reports a 48.8% handshake rate (Afsar 2026), against 66.2% for the npm
servers in our census. That study argues that curated frames select for servers that work, and
reports 66.7% for a hand-curated frame under its own instrument, which is close to our figure.
Our frame is not curated: it is every eligible server in the snapshot, with no popularity filter
and no repair of a server that fails to start. The difference we can name is the snapshot. Theirs
is drawn from a registry of 24,135 servers against the 17,432 in ours, and a registry that grew
from 3,510 to 18,966 servers in 88.6 days (Bharti 2026) is mostly newer entries by the later
date. Whether a newer cohort starts less often is a question a single snapshot cannot settle.

4.2 RQ2–RQ3: Conformance and robustness
Table 2 reports the verdict distribution for each check over the 3,685 responding servers,
with 95% Wilson confidence intervals. Lifecycle and tool-listing conformance are high, and
the discriminating checks are error handling, argument type enforcement, and malformed-
input survival. 7.4% (95% CI 5.9–9.2) of responders failed to reject a wrong-typed required
argument, which Section 4.3 decomposes into the servers that reported the problem anyway
and the smaller class that did not. 0.5% (95% CI 0.3–0.7) failed to recover from a malformed
frame, which we classify as a robustness and conformance failure. The security reading does
not survive the transport: under stdio the client is the parent process and the sole writer to the
server’s standard input, and a party able to deliver a malformed frame can already terminate
the subprocess. JSON-RPC 2.0, on which MCP is built, nonetheless defines a parse-error
response for this case and requires a reply to every subsequent request (JSON-RPC Working
Group 2013), and these servers give neither. One maintainer who reproduced the finding made
this argument, and the classification here follows it (Section 7).
4.3 RQ3 refined: what a failure to reject returns to the client
Thetools-call-invalid-argsverdict records whether a server rejects an argument that
violates its own declared schema. As a protocol judgment that is correct, but it cannot tell a
client what it received, because two different behaviors produce the same verdict. A server
may validate the input and report the problem in the resulttextwithout settingisError, which
is non-conformant but leaves the information available. Or it may execute the tool and return
ordinary-looking output, which does not. We separate the two by classifying the recorded
response of every server in this category (Figure 3, Table 3).

Of 273 such servers, 118 (43%) reported the problem in the result text. The server noticed,
and a client willing to parse prose could too. 129 (47%) executed the tool and returned a result
with no indication that anything was wrong. For 26 the response could not be classified from
the transcript. The hazard class is 3.5% (95% CI 2.8–4.2) of responding servers, smaller than
the 7.4% (95% CI 5.9–9.2) of the raw verdict, and we report the smaller figure.
Splitting the two takes a classifier, and ours is a keyword rule over an English error
vocabulary. To measure what it gets wrong, a human rater labeled a stratified sample of 40
responses against a codebook fixed before any item was read, with the classifier’s answer
hidden. The two agreed on 34 of 40 (Cohen’s𝜅=0.70).
The errors are asymmetric. Of the responses the classifier calls silent execution, the rater
agreed on 95% (19 items), giving a precision of 95%. Of those it files as reporting the problem
in prose, the rater found 24% were tools that had run anyway (21 items), giving a recall of 78%.
Reweighting each stratum by its size in the census puts the true count near 150 rather than 129,
in a range of 110 to 181. The keyword rule under-counts, and 129 is the conservative figure.
We report it as the headline and treat the corrected range as the better estimate of the true rate.

dicting its own published schema has not validated that input. These 129 servers fail an explicit
RFC-2119 requirement, as do the servers that write non-protocol output to stdout, which the
stdio transport forbids with aMUST NOT.

4.5 RQ5: Correlates
We test whether runnability and conformance correlate with the package registry (Figure 5).
Runnability differs: npm servers complete a handshake much more often than PyPI servers
(66.2% of 3,952 against 50.1% of 2,137, a difference of 16.1 pp (95% CI 7.2–23.9)). Confor-
mance does not: the same publisher-cluster bootstrap puts the error-as-result difference at -2.5
pp (95% CI -6.0–1.6), an interval spanning zero. Both comparisons use the same method, and
neither rests on a stronger footing than the other. The pattern follows from RQ4, where the
divergence is inherited from the SDKs and both language ecosystems’ SDKs share the same
default. The registry a server ships on changes whether it starts but not whether it conforms.
Part of this gap came from our own launcher, and we corrected for it. We launch PyPI
servers asuvx <package>, which resolves only if the package’s console script is named
after the package. npm’snpxresolves the entry point frompackage.jsonand has no such
requirement. 462 PyPI servers (21.6% of the PyPI population) installed successfully but were
never launched for that reason and no other. Our classifier identifies 466 such rows in the
census, the completed re-probe covers 462 of them, and 4 were missed. We re-probed those
servers with the entry point resolved from the installed package metadata. 44 (9.5% (95% CI
7.2–12.5)) then completed a handshake, and the rest failed for reasons unrelated to naming
(Python exceptions, hangs, undeclared configuration). Correcting for this and for the launch
arguments (Section 7) raises runnability to 68.4% on npm and 54.3% (95% CI 48.3–61.3)
on PyPI, and the overall census figure to 63.5% (95% CI 59.9–66.5), which we report as the
headline throughout. The npm–PyPI gap moves from 16.1 to 14.1 percentage points and stays
large.
The entry-point problem is also a finding about the ecosystem. Registry metadata does not
record a server’s entry point, and a client working from the registry and nothing else cannot
launch a fifth of published PyPI servers. Once the entry point is resolved, nine in ten of those
servers still fail to start, and a listing in the registry says nothing about either outcome.

6 Discussion
The specification and the SDKs
For whoever decides SEP-2145, accepting it would mostly document practice that already
exists. SEP-1303 reclassified input validation failures as tool execution errors, arguing that
a model can only correct an error it sees (Model Context Protocol contributors 2025), and
SEP-2145 proposes the same for unknown tools (Model Context Protocol contributors 2026).
88.4% (95% CI 86.6–90.0) of responding servers already returnisErrorfor an unknown
tool. Rejecting the proposal would leave nine in ten responding servers non-conformant by
example, and we do not expect 3,258 servers to be changed by hand. The remaining servers
do not form one alternative either: 139 emit a protocol error, 122 emit a different code, and
166 report the failure only in the text of a successful result.
The behavior tracks the SDK rather than the author. The official TypeScript and Python
SDKs and the third-party wrappers built on them all default toisError. So 88.4% (95% CI
86.6–90.0) should not be read as consensus among server authors. It measures SDK adoption.
The practical consequence is that the lever is a small number of libraries, and a change there
reaches thousands of servers at once, in either direction. Section 5 shows the other direction:
one breaking release of the Python SDK stopped 58% of the servers built on it, none of whose
authors changed anything. The limit of that lever is visible here too: the unknown-tool fix
recorded on the TypeScript SDK’s tracker in March 2026 did not move the rate, and the error
still arrives inside a successful response.
Silent execution is a different kind of finding
The unknown-tool case is a disagreement about the error channel, and the client is still told
the call failed. Here the client is told nothing. Input validation is an explicit MUST in the
specification with no pending proposal to relax it, so this cannot be framed as the specification
lagging practice. 114 of the 129 are built on the official TypeScript SDK, whose low-level
ServerAPI publishes a tool’sinputSchemaand does not enforce it (Section 4.3). That looks
like a library gap rather than 129 separate author mistakes.
17
The client can no longer tell the result apart from a correct one. There is no error code,
noisErrorflag, nothing to branch on. An empty feed, returned for top stories with a limit
of"not-a-number", is indistinguishable from a day with no stories, so there is no retry, no
argument repair, and no warning to the user. 129 is a lower bound: we counted any error-like
token in a reply as a report.
Startup failure and what a registry could do about it
Being published does not mean it runs, and the registry carries no signal for it. Pimentel et
al. report the same for notebooks (Pimentel et al. 2021), as do Ibrahim et al. for images that
share a name on Docker Hub (Ibrahim et al. 2020). The registry should attempt a handshake
at publish time and show the outcome: flag it, not delist it. It should also record the entry point
and the required configuration. 462 PyPI servers could not be launched from registry data
alone, and 299 failed for no reason other than undeclared configuration. We ran this check
across 6,089 servers, so it is feasible at registry scale.
What running the servers shows that reading them cannot
Studies that analyze MCP servers from source or metadata (Hasan et al. 2026; Hou et al. 2026)
cannot observe any of these failures. Observing them needs execution. In line with Ait et al.
on Hugging Face Hub (Ait et al. 2025), the registry as a data source is also less reliable than it
looks. Our own launcher undercounted runnability until we corrected the entry-point problem
and passed the launch arguments that registry entries declare: on PyPI, 50.1% uncorrected
against 54.3% (95% CI 48.3–61.3) after.
The two package registries separate the two questions. Runnability differs by 14.1 percent-
age points, 68.4% against 54.3% (95% CI 48.3–61.3), while conformance among the servers
that do run does not. Packaging is per-ecosystem. Protocol behavior is per-SDK. Improving
conformance means fixing a few libraries and improving runnability means fixing thousands
of packages, which are very different amounts of work.
A moving specification
The lifecycle we measure is being retired. Revision 2026-07-28 drops the initialization hand-
shake and negotiates a version on every request instead, with an optionalserver/discover
call for clients that want to ask up front (Model Context Protocol 2026). Our population sits
well behind that boundary: 97% of responders settled on 2025-06-18, and 104 answered with
something older still.
The revision did not wait for authors to adopt it. The official Python SDK released
2.0.0 on the same day, implementing the new revision and renaming a class many servers
import (modelcontextprotocol/python-sdk contributors 2026), and that release is the one the
September re-run found in the output of the servers it lost (Section 5). For a server that declared
the SDK as a range, the new revision arrived as a dependency update its author never chose,
and for most of those servers it arrived as a failure to start. The July census therefore records
this ecosystem immediately before the revision reached it, and the re-run records its arrival.
Behavior measured from now on reflects that transition, and the July census is the baseline
against which it can be compared.
18
Recommendations
The specification should accept SEP-2145, state it with an RFC-2119 keyword instead of an
example, and add the unknown-tool case to the conformance suite so that it is tested.
SDK authors should validatetools/callarguments against the declaredinputSchema
by default, in the low-levelServerAPI as well, and check the tool name againsttools/list.
Most authors never change the default, so the default is the behavior.
Agent framework authors should not treat a result withoutisErroras correct. They
should validate arguments client-side against the schema before the call, and treat a server as
untrusted until it completes a handshake.
Registry maintainers should run a handshake at publish time, show the result, and store
the entry point and the required configuration in the listing.
7 Threats to Validity
Construct validity
Our verdicts operationalize “conformance,” and a poorly chosen operationalization could
over- or under-count. Our checks cover requirements that every revision in the census states
in the same terms, which keeps any server from being judged against a rule that postdates
the revision it negotiated, and we also distinguish normative requirements from illustrative
ones. The most prevalent divergence we report (unknown-tool responses) is graded in its own
error-as-resultcategory and never counted as a failure, because the specification expresses it
only in prose and an example, without an RFC-2119 keyword. We calibrated the harness on
the official reference servers before the study and confirmed it reproduces their known-good
behavior on every check except the SDK-level divergence we set out to measure.
Internal validity
The census ran in the single-phase condition, with the network available during both install
and probe (Section 3.5). This avoids penalizing a server that legitimately contacts the network
during initialization, but it does not remove server-side outbound calls as a confounder. The
exposure is concentrated in one check: fortools-call-invalid-argswe accept anisErrorresult
as evidence that the server rejected the ill-typed argument. AnisErrorproduced instead
by an unrelated runtime or network failure is indistinguishable to the harness, and would be
counted as argument checking that did not in fact occur. The rating pass below puts a number
on that: a quarter of the responses the classifier read as argument checking were, to a human
reader, tools that had run anyway.
A weaker reading of the same verdict deserves stating, because a reviewer will reach
it. The harness poisons one declared property, and for 119 of the 129 silent executions the
poison is the integer12345where the schema declares a string. A runtime that coerces an
integer to a string will then answer a well-formed question correctly, and the code-scanner
example in Table 3 is of that kind: a scanner handed12345, stringifying it, and finding no
imports in"12345"is not obviously wrong. What the check establishes is narrower than a
wrong answer. A server publishes aninputSchema, receives a call that the schema rejects,
and neither refuses it nor signals anything, which is the behavior the specification’s validation
requirement exists to prevent. The remaining 129−119 carry a poison that no coercion rule
19
would repair. A replication that varied the poison by declared type would separate the two
populations, and the released transcripts record what was sent in every case.
A second artifact affects the same check. Where a tool declares several required properties,
the harness poisons one and fills the rest with placeholder values, so a server may reject a
placeholder and never examine the argument under test. We find one such response in the 273
we classified, which bounds the effect at well under a percentage point, and a re-run records
which property was poisoned so the case can be excluded directly. The lifecycle, tool-listing,
error-handling, malformed-input and stdout-purity checks are local protocol behaviors and
are not exposed to this confound. A network-isolated replication would tighten the argument-
checking result, and the harness already supports that condition. Sandbox heterogeneity across
language runtimes is a further source of noise. We bound it by launching each package at the
version its registry entry declares and by recording every run’s full launch command, including
the base-image tag.
External validity
Our population is self-contained, locally-installable servers distributed on npm and PyPI using
the stdio transport. This excludes remote-only servers (which we cannot execute without
provisioning hosted infrastructure) and servers requiring credentials (which we exclude for
both ethics and reproducibility). Section 3.1 gives the size of each excluded class, and every
rate is confined to the stated frame. The largest exclusion is the 7,858 remote-only servers,
which outnumber the frame itself. Whether remote and credentialed servers behave the same
way is untested here. Agent clients mostly launch local stdio servers, and we studied this
population first.
Population counts and publisher clustering
Because we census the eligible frame, the counts are population counts. The intervals we
report do not describe sampling error. They describe how far a rate would move if the registry
had drawn a different set of publishers, which is the uncertainty that matters when a single
publisher ships hundreds of servers from one template. The 6,089 servers in our frame come
from only 3,899 distinct registry namespaces, and the distribution is heavy-tailed: the largest
single publisher accounts for 305 servers (5.0% of the census) and the ten largest for 12.6%.
Servers from one publisher frequently share a template and behave near-identically; a binomial
interval that treats them as independent trials is therefore too narrow. Every interval reported in
the text comes from a bootstrap over publishers rather than over servers. Table 2 and Figure 4
show Wilson intervals, which are narrower, and serve to read the per-check and per-family
distributions rather than to support an inference. The widening is substantial: the handshake
interval is 3.2 times wider than the binomial one (60.5% (95% CI 56.2–64.0) against 60.5%
(95% CI 59.3–61.7)). Error-as-result becomes 88.4% (95% CI 86.6–90.0) and silent type non-
enforcement 7.4% (95% CI 5.9–9.2). As a second check we recompute each rate on a subset
holding one server per namespace (3,899 servers): handshake yield 58.7% (95% CI 57.2–
60.2), error-as-result 85.2% (95% CI 83.7–86.6), silent type non-enforcement 8.1% (95% CI
7.0–9.3), and no conclusion changes under either treatment. The largest publisher is atypical
in runnability at a 26.2% handshake yield, and its presence moves the census figure by 1.8
percentage points.

Validating the response classifier
The split between silent execution and an in-band report rests on a keyword rule, and an
unvalidated rule behind a headline number is exactly the weakness that recent work found in
MCP security scanners (Chen et al. 2026). We therefore fixed a codebook, drew a stratified
sample of 40 responses, and had a human rater label each one with the classifier’s answer
hidden. Agreement was 34 of 40, Cohen’s𝜅=0.70. Precision is 95% and recall 78%, so
the rule seldom invents a silent execution and regularly misses one. Reweighting by stratum
size puts the true count near 150 (110 to 181) against the 129 the rule finds, and we keep the
smaller figure as the headline.
Two limits on that exercise. One rater labeled the sample, so the agreement measures the
rule against a single reader and not the reliability of two independent readers. An earlier pass
by the same rater, used for training and released alongside the labels, is not part of this result:
it was taken at speed and the tool revealed the classifier’s answer after each item, so those
items were no longer blind. The sample reported here is drawn from responses that rater had
not seen.
Severity of the malformed-frame finding, and a limitation it exposed
We initially characterized failure to recover from a malformed frame as a denial-of-service
primitive. A maintainer who reproduced the finding independently argued that this overstates
it, and the argument holds. Under the stdio transport only the launching client writes to that
standard input, and anyone able to send it a malformed frame can already kill the subprocess.
The specification also places the obligation not to send invalid messages on the client. This
paper classifies the behavior as a robustness and conformance failure.
The same maintainer traced the behavior in their own server to the official Go SDK, and
their report changes what this check measures. Their server contains no framing or decoding
code: its stdio path is two lines, and the read loop, the JSON decoding and the decision to
end the session on a decode error all sit inside the SDK. They report the behavior unchanged
from v1.4.1 to v1.7.0, and they ran the same input against the other widely used Go library,
mark3labs/mcp-go, which answers a malformed frame with a-32700parse error and keeps
serving. On identical input the verdict is decided by which library the server links. They have
filed an upstream fix (Go SDK contributors 2026), open at the time of writing, which would
resolve it for every server built on that transport.
Their conclusion is that a per-server dataset that does not separate these is measuring the
SDK rather than the server, and on this check we accept it. Like the unknown-tool divergence,
malformed-jsonrecords a transport default that a server inherits. Another maintainer’s fix
exposed a limitation in our instrument. In their server the process stayed alive while its parser
absorbed the frames that followed, and the nextpingtimed out. Our harness records a single
verdict for “did not answer after a malformed frame” and does not distinguish a terminated
process from a desynchronized one. Both are conformance failures, but they are different
failures with different fixes, and 0.5% (95% CI 0.3–0.7) aggregates the two. Separating them
requires per-server process-state tracking that the released transcripts support but the current
verdict does not encode.
That exchange also exposed a blind spot in our SDK attribution, which the same evidence
lets us size. Attribution resolves npm and PyPI dependency graphs, so a server compiled from

another language and shipped as a binary declares no MCP dependency and falls into theno-
known-SDKresidual whatever it is built on. Of the 17 servers that fail this check, 8 are written
in a language that attribution cannot resolve and 5 of those are Go. The residual therefore
means “no SDK our method can see,” not “no SDK,” and its contrast with the official-SDK
families in Section 4.5 should be read that way. We resolve each repository’s language from
registry metadata and release the table.
Launch arguments the census did not pass
A registry entry can declare arguments a client passes at launch, such as a subcommand that
starts the server. The census read those declarations only to exclude servers whose arguments
are required and have no default, and it passed none of the rest. 522 servers in the frame declare
arguments. A server whose entry says to run it withservewas started without it, printed its
usage and exited, and was counted as failing to start.
We re-probed the 490 servers whose launch command changes when the arguments are
rendered as the registry’s reference describes, through the census’s own code path. In July
24.9% of them completed a handshake; launched as their entries specify, 51.0% do. 143 start
that did not before, and 7 that started without their arguments no longer start with them.
The re-probe ran on the date of the September re-run, after the Python SDK’s breaking
release and after some packages had been withdrawn, so its failures mix two causes. 8 servers
that started in July fail in the re-probe for one of those reasons; that says nothing about
their arguments, and they keep their July outcome. Only failures the arguments themselves
cause count against a server, and recoveries count in full, since drift stops servers rather than
starting them. The headline figure is corrected by that rule. It remains a lower bound: 24
servers that did not start in July fail in the re-probe on the SDK’s signature, and whether their
declared arguments would have started them in July cannot be recovered. Conformance rates
are computed on the servers that started in July and are not recomputed; a server that started
without its arguments may have run in a different mode from the one its entry specifies.
Interrupted probes
49 probes (0.8%) ended for reasons that may lie outside the server (Section 3.5): 32 killed by
the memory cap or the disk guard, and 17 aborted by a harness-side error. Counting 48 of
them as non-handshaking can depress the handshake yield by at most 0.8 percentage points
and does not affect conformance rates. Each is identifiable in the released census rows by its
exit code or its missing verdicts.
Reproducibility
Every number in this paper is regenerated by the released analysis scripts from the released
census rows, and we have checked that the regenerated values match the ones printed here,
including from a fresh clone that holds only the release. The harness ships with a test suite
that runs the probe against small servers built to exhibit each behavior the paper reports, and
asserts the verdict for each. They range from a fully conforming server to the SDK default to
one that dies on a malformed frame. The same suite checks the startup classifier, the interval
arithmetic, and that no released file names a server the dataset withholds. It runs on every
change. The registry snapshot, launch commands, and package versions are recorded. Census
22
rows do not record the harness commit, but the code that produced them is taggedcensus-v1,
and the probe logic there is unchanged from the version that was calibrated.
The registry changes daily, and the object of study is the snapshot of 19 July 2026. A
longitudinal study of the same registry shows how fast it moves, growing from 3,510 to 18,966
servers over 88.6 days (Bharti 2026).
8 Ethics and Responsible Disclosure
This study executes third-party code and probes servers for defects, and it follows the norms
of responsible measurement research.
Safe execution
Every server runs inside an isolated container during both installation and probing, with all
Linux capabilities dropped, no new privileges, bounded memory, CPU and process counts,
and no host filesystem access. The census was executed in the single-phase condition, where
install and probe share one ephemeral container and the network is available throughout.
The install phase executes arbitrarypostinstalland build scripts, and it receives the same
isolation as the probe. Server code also had network access while being measured, and to
limit the risk every container is discarded after a single server, while the entire census ran
on a disposable cloud instance with no credentials attached. Untrusted code could reach no
further than one throwaway host. The harness also supports a network-isolated probe phase
(--network=none), which we recommend for replications that do not need install and probe
in a single pass. We execute no server that declares a requirement for credentials, both because
it lies outside our frame and because doing so could send real requests to third-party systems.
Observed side effects of networked measurement
Because the census ran with the network available, we audited the captured output for evidence
that server code produced effects outside its container. At least 1.4% of servers attempted
an outbound connection that failed and logged an error. A successful connection leaves no
trace in the captured output, and this figure is a lower bound. Our redactor caught credential-
shaped values in the output of 5 servers, and on reading each one, four were live: three
printed session tokens they had generated for local use, and one auto-provisioned an API key
and account against a third-party service. The fifth printed a configuration example whose
key was a placeholder. The provisioned key is the class our frame’s exclusion of credential-
requiring servers was meant to prevent, and we have redacted every such value from the
released dataset and asked the service to revoke the provisioned key and delete the account.
Excluding servers thatdeclarerequired credentials does not exclude servers thatacquirethem
unprompted, which makes declaration-based eligibility filtering a weaker ethical guarantee
than it appears. A network-isolated probe phase should be the default for measurement at
this scale, and we recommend replications use the harness’s two-phase mode. We used the
single-phase condition because it let one disposable host run the whole ecosystem, and the
side effects above are what it cost.
23
Responsible disclosure
Some of our findings concern robustness. A server that stops serving after a malformed
frame can desynchronize or strand a connected client, and so can a server that emits non-
protocol bytes on its stdio channel. We report these only in aggregate and through anonymized
case studies, and we do not publish a name-and-shame list of individual servers. Security-
relevant findings are recorded in a private disclosure log with maintainer contacts resolved
from registry repository metadata. We reported 15 of the 17 servers that stop serving after
a malformed frame to their maintainers through their issue trackers; the remaining 2 list no
repository we could reach. At the time of writing 6 of those reports are closed as resolved,
and 5 of the projects have published a release since closing them. One maintainer corrected
our severity assessment, and the paper follows that correction (Section 7). We also reported
the input-validation gap in the TypeScript SDK’s low-levelServerAPI (Section 4.3) to the
SDK maintainers, who have labeled it for design work on both the 1.x and 2.x lines. We did
not open an issue against each of the 129 servers that run a tool on an argument their own
schema rejects. The defect we identify there belongs to the library. 114 of them are built on
the SDK whose low-level API publishes a schema it does not enforce, and a per-server report
would tell an author their code is at fault where our own analysis says it is not. Notices are
drafted and released with the harness so that any maintainer can check their own server, their
identities are withheld from the dataset, and the report went to the SDK, which can fix it. The
remaining findings concern unknown-tool handling and stdout contamination, and they are of
lower severity and appear only in aggregate.
The released dataset withholds the identities of all 321 servers carrying a security-relevant
finding, replacing each name with a stable pseudonym so the rows remain linkable across files.
That set includes every server in the silent-execution class. Naming a server beside a transcript
of it answering a poisoned call is a claim about its author’s work. The empirical standard for
secondary data asks that the reputation of the subjects be respected in the reporting of a study
as well as in its conduct. The registry snapshot in the release carries the same pseudonyms,
so the withheld set cannot be recovered from the release by subtracting the servers the census
names from the servers the frame lists. The registry itself is public, and someone who compared
the release with an archived copy of it could still recover which servers were withheld. The
comparison cannot reveal which finding belongs to which server, nor any transcript, and we
withhold both. Identities are restored only where a maintainer has fixed the defect or asked to
be named.
Registry and maintainer impact
Our crawl pages sequentially through the registry’s public API and backs off on errors. Our
installs draw each package once per probe from its public registry in the ordinary way. The
released harness lets any author check their own server’s conformance before publishing.
9 Conclusion
Earlier studies measured the MCP server ecosystem statically, or ran servers to look for
vulnerabilities. We installed every eligible server in the official registry, launched each in a
disposable sandbox, and tested whether it follows the protocol.
24
Of the installable servers, 63.5% (95% CI 59.9–66.5) complete a handshake. The rest
never serve the protocol, for the reasons broken down in Figure 2. Of the servers that respond,
88.4% (95% CI 86.6–90.0) report an unknown tool in the same way, and the cause is the SDKs
they are built on as a direct dependency or through a third-party wrapper. An open proposal
would change the specification to match this behavior, and our numbers show how much of
the ecosystem it already describes. A smaller group, 3.5% (95% CI 2.8–4.2), run a tool on
input their own schema rejects and return an answer with no sign that anything is wrong.
One, asked for top stories with a limit that is not a number, returned an empty feed, and the
specification makes input validation a requirement these servers do not meet.
Re-running the same servers sixty-nine days later showed how far that dependence on
the SDKs reaches. A breaking release of the official Python SDK, published nine days after
our snapshot, stopped 58% of the Python-SDK servers that had worked, through dependency
ranges their authors never touched, and pinning the SDK below it restores them. Conformance
among the servers that still ran did not change.
A static scan or a registry crawl shows none of this. The harness and the dataset are public,
and others can repeat the measurement, extend it to remote and credentialed servers, or check
their own servers before publishing. Because the error-reporting and input-validation behavior
comes from a few SDKs, it can be changed there, and the re-run shows that a change there
reaches a large part of the ecosystem at once, whichever direction it goes.
