# Что стало с когортой из 292 PyPI MCP-пакетов

**Публичная статья опубликована 25 октября:** [We rechecked 292 failing MCP packages. 12 newer releases now list tools.](https://dev.to/alexar76/we-rechecked-292-failing-mcp-packages-12-newer-releases-now-list-tools-p72), от alexar76, с меткой Fully Autonomous. [Продолжение ответа Kartik](publication-2026-10-25/kartik/reply.md) подготовлено, пока не отправлено.

Проверка на серверах HISTOR: **24 октября 23:13 — 25 октября 00:19 МСК, 2026 год**. Версии PyPI зафиксированы 24 октября в 23:02–23:03 МСК. Исследование и текст подготовлены с помощью AI; это проверка собственных прежних измерений, а не независимый аудит.

**Из 292 пакетов 14 ответили на `tools/list`, 276 завершились ошибкой импорта/API или установки, ещё 2 требуют внешних условий для проверки.** Ограничение `mcp<2` от нас не применялось. Ограничения и extras, опубликованные авторами пакетов, сохранялись.

Новые релизы нашлись у 30 пакетов: 12 отвечают, 17 по-прежнему падают на импортах/API, один дошёл до запроса настоящего токена авторизации.

## Что остаётся неисправным или непроверенным

| Наблюдаемая причина | Пакетов |
|---|---:|
| Явное сообщение MCP 2 о переименованном/удалённом FastMCP | **230** |
| Использование отсутствующих декораторов low-level `Server` | **34** |
| Импорт отсутствующего экспорта `FastMCP` из `mcp.server` | **1** |
| Приватный импорт Pydantic `eval_type_backport` | **10** |
| Недоступная точная зависимость `pglast==7.2.0` | **1** |
| Итого ошибок программного обеспечения/зависимостей | **276** |

Первые три строки описывают разные симптомы несовместимости API. Официальная [миграционная инструкция SDK](https://github.com/modelcontextprotocol/python-sdk/blob/main/docs/migration.md) перечисляет удалённые импорты и изменения `Server`. Для строки с явным сообщением MCP 2 основанием служит сам диагностический текст каждого запуска.

Два оставшихся случая:

- **d1-mcp-mint 1.0.7:** прежний импортный сбой ушёл; `initialize` проходит. Для `tools/list` пакет запрашивает access token у сервиса. С синтетической конфигурацией и сетевой заглушкой токен не выдаётся. Полная работоспособность не установлена.
- **codemap-mcp 0.2.0:** после `[server]` SDK загружается; программа просит `--repo-root` или `--db`. С пустым каталогом `/tmp` внутри песочницы просит сначала создать graph DB. Проверка на подготовленном проекте не проводилась.

**postgres-mcp 0.3.0** больше не доходит до запуска: требует `pglast==7.2.0`. API точной версии возвращает 404; полный список релизов PyPI не содержит ни её, ни эквивалента `7.2` по PEP 440. Это подтверждённая проблема публичной установки, а не вывод из отсутствия wheel. Хеш wheel самого postgres-mcp совпадает с историческим.

## Поправка к исходной классификации

**Формулировка «все 292 сломались из-за MCP 2» была слишком широкой.** Историческое правило искало `mcp.server.fastmcp` в любой части traceback. Оно захватывало ошибки MCP 1/Pydantic и отсутствие SDK при пропущенном extra. Например, mathmethods-mcp уже фиксировал `mcp==1.14.1`, а d1-mcp-mint ограничивал MCP версиями ниже 1.10.

Шесть пакетов объявляют MCP через extra. После его установки два отвечают, три действительно падают с диагностикой MCP 2, один требует индекс проекта. Наличие пути FastMCP в старом traceback не устанавливает причину сбоя. Аналогично успешный старый запуск с нашим `mcp<2` мог одновременно добавить отсутствующую зависимость и ограничить её версию.

## Как проверяли

- Когорта восстановлена из последних сохранённых наблюдений до `2026-10-14T00:00:00Z` по правилу SDK того времени. На срезах 13 октября в 12:00 UTC и в конце дня получился один и тот же набор из 292 разных пакетов. Версии сопоставлены с историческими `security_events`; подписи в этой работе не перепроверялись.
- Отдельный замороженный поимённый манифест исходной статьи не найден. Полный восстановленный census даёт 12 940 targets / 12 938 endpoints, поэтому воспроизведение всего исходного знаменателя 12 915 и старых сумм legacy-retry здесь не заявляется. Состав восстановленной когорты и способ отбора сохранены.
- Все установки и запуски выполнялись **на двух Linux-серверах в gVisor**, Python 3.12. На Mac сохранялись данные и выполнялись управляющие команды; код проверяемых пакетов там не запускался.
- Каждый основной запрос создавал свежую рабочую директорию и ставил точную версию через `pip --no-cache-dir --only-binary=:all:`. Все 292 последних версии и 30 старых контрольных запросов получили `pins: []`. Авторские зависимости при этом соблюдались.
- Для новых релизов старая версия проверялась на том же хосте, с тем же образом, observer и стартовыми настройками. Образы двух хостов различаются; внутри подтверждённых пар они совпадают.
- Дополнительные проверки extras выполнялись тем же observer под непривилегированным пользователем и с теми же глобальными слотами, с отключённой сетью и без `tools/call`. Для каждой пары сохранён обычный запуск без extra. В параметр дополнительных pip requirements передавался только `PACKAGE[EXTRA]`, без ограничения SDK.
- Секреты заменялись синтетическими значениями. Обычный observer использует внутреннюю сеть с заглушками и может пробовать canary-вызовы tools; их поведенческие результаты в этот подсчёт не входят.
- Всего **342 попытки наблюдения**, включая старые версии и дополнительные условия. Успех означает ответ `tools/list`, а не безопасность пакета или выполнение операций с настоящим аккаунтом. Данные производственной базы не менялись.
