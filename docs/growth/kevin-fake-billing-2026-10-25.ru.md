# Kevin Hall: контролируемый тест платного действия по умолчанию

Проверено 25 октября 2026 года. [Вопрос Kevin](https://dev.to/alexar76/we-installed-12915-mcp-servers-and-started-each-one-41-never-answered-3heh#comment-3hmmh) касается canary, который может успешно выполнить бесплатный путь и не проверить платный путь по умолчанию. Новый эксперимент воспроизводит этот пробел: **текущий canary выбрал `preview` и потратил 0 фиктивных кредитов; вызов того же tool с `{}` потратил 7**. Это отдельная контролируемая проверка; исходный census не измерял такое поведение.

## Что запустили

Наш синтетический stdio MCP-сервер `lookup_record` принимает необязательный `mode`: `preview` или `purchase`. В основной конфигурации schema указывает `default: "purchase"`, а handler действительно реализует этот default при пустых или отсутствующих arguments. Обычный успешный ответ содержит только `recordId` и `status`, без квитанции или признака списания. В бесплатном парном контроле definitions и ответы сохранены, а биллинг отключён.

Фиктивные списания подтверждает отдельный от Node MCP-сервера backend: поток в Python-процессе контроллера, доступный по Unix socket. Только backend пишет авторитетный `billing.jsonl`; журнал самого MCP-сервера хранит полученные квитанции. Используются целые mock credits, UUID операции и изолированный журнал на каждый прогон. Реальных денег, платёжных провайдеров и сторонних MCP-серверов здесь нет.

Выполнение: `admin-vps`, **Linux amd64, Docker runtime `runc`, `--network none`**, Node **22.23.3**, Python **3.11.2**. Это не gVisor-прогон; syscall trace не собирался. Проверен опубликованный npm-артефакт **`@aimarket/warden@0.21.0`**, SHA-256 `5cc9aec04fc753adeb2ab97264c571e625b65bb57b43de2541dd4cf6260bc1f1`. Для HISTOR выполнены `talk` и `canary_args` из текущего файла `histor/sandbox/histor_observe.py`, SHA-256 `1faf6274afad8add71e5b8c8eb6bd1874792f936e0f25b3377af91e8440b7f5e`. Это фиксирует проверенную версию observer, но не устанавливает, что исторический census исполнял те же байты. [Входные hashes](../evidence/kevin-fake-billing-2026-10-25/input-manifest.json) и [точные команды](../evidence/kevin-fake-billing-2026-10-25/execution.json) сохранены.

## Результат

**26 сценариев × 3 повтора: 78 из 78 прошли заданные проверки.** Backend отдельно прошёл **30 self-checks**. В каждом повторе получены следующие результаты:

| Сценарий | Фиктивные кредиты | Наблюдение |
| --- | ---: | --- |
| Текущий canary HISTOR | 0 | Успешно вызвал tool с `mode: "preview"`; платный default не достигнут. |
| `{}` / arguments отсутствуют | 7 / 7 | Handler применил `purchase` по умолчанию. |
| Явные `preview` / `purchase` | 0 / 7 | Контроль двух ветвей handler. |
| Неверный placeholder в `mode` | 0 | Ошибка валидации до обращения к биллингу. |
| Default скрыт из schema, handler прежний | 7 | Отсутствие schema default не устраняет серверный default. |
| `mode` обязателен, передано `{}` | 0 | Сервер отказал до списания. |
| Списание перед `isError` / перед timeout | 7 / 7 | Ошибка и отсутствие ответа не означают отсутствие эффекта. |
| `readOnlyHint: true` | 7 | Заявленная annotation не удостоверяет биллинг backend. |
| Повтор с тем же idempotency key | 7 всего | Два вызова дали одно списание в backend. |

Парное сравнение платного и бесплатного серверов прошло **3 из 3**: направления и JSON-сообщения полного MCP-обмена одинаковы, а независимые журналы показывают **7 против 0**. При сравнении исключены технические sequence/timestamps журнала; это не утверждение о равенстве времени выполнения или сырых транспортных байтов. Результат показывает ограничение вывода по MCP-обмену без доступа к биллингу. [Сводка всех сценариев](../evidence/kevin-fake-billing-2026-10-25/results/result.json), [реальный вызов canary](../evidence/kevin-fake-billing-2026-10-25/results/cases/histor-current-canary/01/transcript.json) и [списание перед ошибкой](../evidence/kevin-fake-billing-2026-10-25/results/cases/charge-before-tool-error/01/billing.jsonl) доступны локально.

## Что показал WARDEN 0.21.0

Обычный `wrap` пропустил `{}` без запроса approval: backend записал 7 кредитов. Явное описание цены у `purchase_report` также само по себе не включило approval. В проверенном настроенном policy `sensitiveToolPatterns` совпадал с именем tool; тогда отсутствие UI, decline, accept без отметки `run: true` и `--ask refuse` блокировали вызов до handler, списаний не было. Явный scripted accept с `run: true` разрешил один вызов и 7 кредитов; следующий вызов запросил новое подтверждение и был отклонён. [Точный approval-обмен](../evidence/kevin-fake-billing-2026-10-25/results/cases/warden-sensitive-accept/01/transcript.json) содержит аргументы и разрешение запуска, но не финансовую котировку или лимит суммы.

Дополнительные adversarial controls размещали списание прямо в `initialize` и `tools/list`: оба дали 7 кредитов, в том числе с sensitive policy. Такой policy контролирует вызовы tools; эти контрольные эффекты происходят до них. Они не устанавливают поведение обычных серверов.

Это проверка механизма на собственной fixture. Apify и другие реальные сервисы не проверялись; доля таких серверов в census, реальные платежи и осведомлённость людей не измерялись. Ответы на approval генерировал тестовый клиент. Новый текст Kevin подготовлен локально и не отправлен.

Перед [удалением временного каталога](../evidence/kevin-fake-billing-2026-10-25/cleanup.json) сверены 5 входных и 475 выходных файлов. Исходники и результаты сохранены локально.
