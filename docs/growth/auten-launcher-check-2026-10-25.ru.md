## Как именно работает launcher

Опубликованный npm-архив 0.1.5 скачан и проверен по registry SHA-512 integrity и
SHA-1. Код прочитан как текст, **Auten не исполнялся**.

В `bin/auten-mcp.js` поиск runner идёт в таком порядке:

1. Существующий путь из `AUTEN_BIN`.
2. Стандартное место установки (`~/.local/bin/auten` на Unix, свой каталог на Windows).
3. Первое существующее совпадение в `PATH`.

Если runner найден, launcher запускает его с аргументом `mcp-bridge` и передаёт
stdio. Если не найден — сам отвечает по MCP единственным `install_auten`.
Поэтому даже одинаковые версии npm и `PATH` ещё не означают один и тот же runner:
важны `AUTEN_BIN` и стандартный путь, который проверяется раньше PATH.

Текущие официальные инструкции поддерживают оба варианта: `auten mcp-bridge`
и npm launcher. Для проверки именно launcher нужно сохранить путь через npm
либо его установленный executable, **а прямой запуск bridge отметить отдельно**.
Воспроизводимый npm-вариант команды:

```sh
npx -y @autenai/mcp@0.1.5
```

Это команда для нового согласованного сбора, а не утверждение о точном argv
старого запуска HISTOR или фактической конфигурации автора.

В timeline HISTOR стоит `serverVersion: 0.1.4`, хотя текущая запись пакета — 0.1.5.
Исходник `histor/histor/app.py` объединяет одинаковые status/toolset/subject в
один интервал и оставляет там metadata первого наблюдения. Опубликованный
launcher 0.1.5 берёт initialize-version из собственного `package.json`.
Поэтому старое поле timeline **не доказывает ошибку версии в launcher** и не
заменяет provenance отдельного запуска.

## Что подготовлено для настоящего сравнения

Отдельный локальный [сборщик](https://github.com/alexar76/warden/blob/main/examples/launcher-evidence/collect.mjs)
использует клиент и MTL-канонизатор опубликованного WARDEN 0.21.0. Инструкция:
[launcher-evidence](https://github.com/alexar76/warden/blob/main/examples/launcher-evidence/README.md).

Он запускает только указанную владельцем команду, получает initialize и все
страницы tools/list, сохраняет tools, initialize metadata, argv, платформу,
версию Node/WARDEN, сообщённую владельцем версию runner, SHA-256 файлов и digest.
Он не вызывает инструменты, не создаёт trust pins и ничего не загружает в HISTOR.
`tools.json` — полный результат клиента WARDEN, а не буквальные сетевые байты:
клиент нормализует отсутствующие description/inputSchema; это записано в capture.

Штатный `declare --out` сохраняет лишь digest/count/when, поэтому его файл
**не заменяет снимок tools**. Экспорт через `scan --update-lock` создавал бы
решение о доверии; для нейтрального сбора его не использовали.

Сборщик проверен **10 тестами на Linux** с опубликованным WARDEN 0.21.0 в
Docker/runc без сети. Первая проверка выявила различие внутренних модулей
публичного пакета и текущего source; список зависимостей исправлен, повтор прошёл
10/10. Оба прогона сохранены. Это тесты собственных синтетических MCP-ответов,
не исполнение Auten. [Лог](../evidence/auten-launcher-2026-10-25/tests.log) и
[метаданные](../evidence/auten-launcher-2026-10-25/test-execution.json).

## Что ещё должен предоставить Auten

Для двух различающихся окружений достаточно следующих данных:

1. Версия launcher и точная команда в виде command/args. Желательно одна и та же
   закреплённая версия 0.1.5 в обеих средах, без `latest`.
2. ОС/архитектура и версия/артефакт runner; если runner отсутствует — явно `absent`.
   Если выбран файл через AUTEN_BIN — отметить это. Путь можно обозначить без
   личного имени пользователя; для идентификации артефакта полезен SHA-256 файла.
3. Два пакета сборщика: среда без runner и среда с runner либо два реально
   различающихся runner-окружения. Одни digest/count не заменяют tools.json.
4. Только имена необходимых env-переменных и описание различий условий.
   Полный конфиг, значения env, API keys и персональный SSE URL не нужны.

Владелец просматривает tools/initialize/argv перед передачей: сервер может
включить в определения частные сведения. Автоматической отправки нет.
Не нужно удалять рабочий runner ради проверки: можно использовать существующую
тестовую среду или передать один новый рабочий снимок для первого сопоставления
с явно более старым sandbox baseline. Последнее не изолирует влияние ОС/версии.

После получения проверяем hashes и digest, перечисляем добавленные/удалённые
tools и изменения схем/описаний, затем проверяем декларацию как слово издателя,
а не наблюдение HISTOR. Синтетические fixtures сборщика не засчитываются как
второй реальный набор Auten.
