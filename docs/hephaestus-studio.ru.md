## Что это

HEPHAESTUS собирает цепочку рыночных возможностей, **считает её стоимость до того, как что-либо
оплачено**, отправляет исполнителю конвейеров и сохраняет подписанный bill of materials
(спецификацию работ), который приходит обратно, — включая указание на хоп, виновный в отказе
цепочки.

Это не универсальный конструктор рабочих процессов. Каждый узел — реальная строка подписанного
манифеста хаба: с ценой, объявленной задержкой и заявленным объёмом свидетельств о надёжности.
В этом и вся разница: такой граф может ответить, *сколько это будет стоить* и *кто это сломал*, чего
не даст никакая отрисовка прямоугольников.

Две поверхности, разделённые сознательно:

| Поверхность | Роль |
|-------------|------|
| Узел `hephaestus` в Alien Monitor | **Наблюдение.** Реальные прогоны — стоимость, хопы, виновный хоп — плюс какая часть каталога вообще пригодна к соединению. |
| Страница студии | **Сборка.** Выбрать возможности, заполнить параметры, увидеть смету, отправить. |

Монитор наблюдает, но не содержит редактор. Поверхность наблюдения, которая выдумывает ленту, хуже
пустой, поэтому при отсутствии прогонов панель прямо об этом и говорит.

## Страница студии

Хаб отдаёт её по адресу **`/studio`**, и это не произвольный выбор: каталог, из которого
она собирает граф, — это собственный подписанный манифест хаба, а CORS у хаба fail-closed,
поэтому страница, размещённая где-либо ещё, прочитать его не смогла бы. Один origin, без
мостика и без второго домена.

Запуск тоже идёт с того же origin. Исполнитель конвейеров — отдельный сервис, и браузер не
достанет его кросс-доменно, поэтому хаб пробрасывает один запрос через `POST /studio/run`.
Этот проброс сознательно узкий:

* адрес назначения берётся из `AIMARKET_PIPELINE_EXECUTOR_URL` на хабе и **никогда из тела
  запроса** — проброс, берущий цель у вызывающего, это SSRF-гаджет, как бы он ни назывался,
  а этот доступен из любого браузера;
* не задано — значит `503` с прямым указанием переменной, а не догадка про какой-нибудь
  локальный порт;
* тело проверяется по форме и размеру до того, как что-то уйдёт с хаба, с тем же лимитом в
  шестнадцать узлов, что и у исполнителя;
* учётные данные вызывающего не пробрасываются: путь запуска из студии — бесплатный
  (sandbox), а платный прогон идёт к исполнителю напрямую со своим каналом.

Ответ несёт `trace_url`, поэтому страница ссылается на подписанный bill of materials, а не
просит верить собственной сводке.

```bash
cd hephaestus/studio && npm install && npm run build   # соберёт dist/, который отдаётся на /studio
```

Результаты сборки в этом репозитории не хранятся, поэтому бандл собирается отдельной
Node-стадией в образе хаба (сам runtime-образ только на Python). Деплой, где
`hephaestus/studio/dist` всё же не оказалось, отвечает `503` и называет недостающую сборку,
а не 404.

Ниже 900px **фактической ширины** приложения три колонки превращаются в одну за раз — каталог, канвас, проверки — с
переключением нижней панелью: при 375px палитра и инспектор оставляют канвасу несколько
пикселей, а канвас — та панель, которая обязана быть рабочей. Смета остаётся в шапке в обоих
режимах: ради неё страница и существует. Добавление модуля переводит на канвас, а касание
модуля — к его параметрам, чтобы касание никогда не попадало в панель, которую не видно.

Порог измеряется на самом элементе через `ResizeObserver`, а не спрашивается у вьюпорта:
окно может быть физически узким, сообщая при этом широкий CSS-вьюпорт — десктопный
user-agent на телефоне, отмасштабированное или уменьшенное окно, встроенный фрейм, — и
медиазапрос во всех этих случаях остаётся ложным, пока канвас сжат в полоску.

## Визарды — цель, решённая против каталога

Визард — это цель плюс упорядоченный список **ролей**. Роль — предикат над тем, что
возможность *объявляет*: какие поля отдаёт, какие требует, как выглядит её идентификатор, —
и никогда не над вбитым `product_id`. Поэтому визард не может предложить строку, которой нет
в продаже, и продолжает работать при изменении каталога; курируемый список рецептов не даёт
ни того, ни другого.

Подбор берёт по одной возможности на роль, в таком порядке предпочтений: сколько данных шаг
получает от предыдущего, потом сколько остаётся вписать руками, потом есть ли за строкой
измеренные наблюдения, и только потом цена. Цена последняя намеренно: самая дешёвая цепочка,
которая не делает работу, — не экономия.

Две защиты, и обе появились потому, что живой каталог сломал наивную версию:

* **`consumes`** — хотя бы одно связанное поле должно соответствовать тому, что роль обязана
  получить. Без этого `platon.random@v1` соединялся с `platon.beacon@v1` по `num_bytes`:
  розыгрыш эхом отдаёт свой же параметр, а маяк принимает этот параметр на вход — связь
  выглядит чистой и не проверяет ничего. Шаг, потребляющий *параметры* предыдущего, не
  потребляет его *результат*.
* **`sameProductAsPrevious`** — для криптографического материала это корректность, а не
  вкус. `proof` — имя поля, а не формат: подборщик спокойно отправил VRF-пруф от
  `platon.random@v1` в `chronos.verify@v1`, верификатор VDF, потому что поле в обоих зовётся
  `proof`. Такая цепочка выставит счёт за первый шаг и упадёт на пруфе, который второй не
  разберёт. Для обычных данных — показания, локации — ограничения нет: там второе мнение от
  *другого* поставщика дороже, чем от того же.

Цель, для которой закрыты не все роли, возвращается **недоступной, с указанием сломавшейся
роли**, и меню показывает её с этой причиной, а не скрывает. Сегодня недоступны две из
четырёх, и обе причины — настоящие пробелы: верификатор для собственных розыгрышей `platon`
никто не продаёт, а `atlas.situation.brief@v1` требует рамку (`west/south/east/north`),
которую в каталоге не отдаёт никто — `atlas.point.read@v1` отдаёт объект `point`. Визард,
который тихо выкинул бы пропущенный шаг, вручил бы человеку цепочку, делающую не то, что
обещано в её названии, и человек заплатил бы за это до того, как узнал.

## Смета

Честность числа держат два правила, закреплённые тестами в [`hephaestus/tests/estimate.test.ts`](https://github.com/alexar76/hephaestus/blob/main/tests/estimate.test.ts):

1. **Возможность без цены называется по имени и никогда не считается бесплатной.** Она исключается
   из итога и перечисляется отдельно: итог, молча поглощающий неизвестное, — не смета.
2. **Деньги суммируются целыми микродолларами.** Реальные цены каталога — это чтение датчика за
   $0.001 и вызов оракула за $0.004; сложение таких величин в плавающей точке уплывает ровно в тех
   разрядах, из которых состоит итог.

Там, где хаб маршрутизирует к пиру, берётся маршрутизированная цена: считать цену провайдера значило
бы недооценить каждый федеративный хоп на величину сбора за маршрутизацию.

Задержка показывается как самый длинный путь по объявленным задержкам, то есть как **нижняя граница**:
исполнитель сегодня проходит хопы последовательно, поэтому быстрее реальный прогон быть не может.
Возможности без объявленной задержки считаются нулём и перечисляются по имени, так что число никогда
не раздувается догадкой.

## Надёжность, которой можно верить — правило `reputation_basis`

Манифест хаба публикует `success_rate_30d` для каждой строки. Для строки, которую никто ни разу не
вызывал, это число — сознательно выбранная нейтральная заглушка: краулер игнорирует заявленные пиром
показатели успеха, потому что пир, способный объявить себе 99%, захватил бы маршрутизацию с первого
индексирования.

Следствие: все 76 строк живого каталога публиковали `0.5`, и ничто в документе не отличало
измеренную «одну из двух» от незаполненной заглушки. Теперь манифест несёт свидетельство рядом с
числом:

| Поле | Значение |
|------|----------|
| `observations_30d` | Вызовы, которые публикующий хаб наблюдал за последние 30 дней. |
| `reputation_basis` | `measured` — показатель равен успехам/попыткам за это окно. `unobserved` — ничего не выполнялось, показатель является заглушкой. |
| `by_hub[*].trust_basis` | Двойник на уровне пира: `measured`, `unobserved` или `self` для самого публикующего хаба. |

**Правило для любого потребителя, включая наш собственный интерфейс: опираться на
`reputation_basis`, а не на число.** Если основание не `measured`, показывать «вызовов ещё не было»,
а не оценку. Ядро вообще отбрасывает значение, а не передаёт его дальше
([`hephaestus/src/catalog.ts`](https://github.com/alexar76/hephaestus/blob/main/src/catalog.ts)); хаб старше этих полей читается как
`unknown`, а это не то же самое, что «плохо».

Как только возможность вызвали, манифест отдаёт **измеренный** показатель — комментарий в краулере
всегда утверждал, что хаб считает его сам; не считал никто, поэтому `0.5` было заморожено в каждом
подписанном манифесте.

## Соединяемость — почему часть строк вообще нельзя подключить

Возможность соединяема только если объявляет поля входа (объект `properties`, пусть даже пустой —
«не принимает ничего» это ответ) **и** непустую схему вывода. Строки, не выполняющие хотя бы одно из
условий, находимы и имеют цену, но не могут быть соединены с соседом, и студия говорит об этом
вместо того, чтобы рисовать порт, ведущий в никуда.

Чтобы каталог стал соединяемым, закрыты три пробела на стороне источников:

* **Platon, 9 возможностей.** Агрегатор oracle-family федерировал Platon только по идентификатору,
  описанию и цене, поэтому каждая строка наследовала дефолт oracle-core «полей нет», тогда как сам
  Platon документирует `num_bytes`, `client_seed`, `prompt`, `round`, `question` и остальные.
  Теперь агрегатор пробрасывает собственные объявления Platon, а не пересказывает их: всё
  пересказанное руками — это тот самый дрейф, из-за которого однажды продавался `platon.verify@v1`.
* **ATLAS, 6 SKU.** Ключ `output_schema` отсутствовал целиком: шесть платных артефактов решений,
  форму результата которых покупатель мог узнать, только купив один. Теперь схемы отражают то, что
  строят обработчики, и набор тестов проверяет реальный вывод против них в обе стороны: схема не
  вправе переобещать и не вправе отставать от обработчика.
* **Возможности, которые действительно не принимают входа** (`platon.state@v1`,
  `platon.commit@v1`, `gaia.fleet.status@v1`) объявляют явно пустой `properties`. Это правильно, а
  не сломано: «не принимает ничего» и «не говорит» — разные состояния, и студия отображает их
  по-разному.

## Что исполнитель умеет выразить, а что нет

Студия отказывает графу, который исполнитель не сможет выполнить, и называет причину — вместо того
чтобы выгрузить JSON, который позже упадёт или, что хуже, выполнится, накормив хоп данными не от того
предшественника.

* **Не более 16 возможностей на конвейер** (`PipelineRequest.nodes`). Более крупную работу нужно
  делить на этапы.
* **Один родитель-источник данных на хоп.** `input_from` называет один узел, поэтому источником
  данных можно отметить ровно одну входящую связь; остальные выражают только порядок.
* **Хопы идут последовательно.** Оценка задержки — нижняя граница, а не прогноз.

### `input_from` называет узел

`input_from` объявлен как идентификатор узла, а реализован был как флаг: любое непустое значение
подкладывало результат того хопа, который завершился последним. В прямой цепочке это совпадает.
В DAG — нет: хоп с двумя родителями получал результат того из них, который топологическая сортировка
случайно завершила вторым. То есть граф со сведением можно было нарисовать, оценить, оплатить — и
накормить не тем предшественником, с действительной подписью на bill of materials.

Теперь поле называет именно того родителя, которого имеет в виду, а результаты хранятся по узлам, так
что назвать можно и дальнего предка. Значение, не совпадающее с известным узлом, сохраняет старое
поведение «последний результат», поэтому существующие вызывающие стороны не затронуты.

## Запуск: кто выполняет и кто платит

Хоп, который эта фабрика не хостит, маршрутизируется в федеративный invoke хаба — потому что
студия собирает граф из каталога хаба (76 строк, все от пиров), а у исполнителя своих
девять. До появления этой маршрутизации любой граф, который мог собрать посетитель, отвечал
`404 capability not found`.

Решать пришлось не код, а деньги:

* **Ни одна учётная запись исполнителя не прикладывается.** Кнопка Run без аутентификации,
  тратящая баланс оператора, — это открытый кран, и каждый выпущенный ею чек называл бы
  неверного покупателя.
* **Личность пробного тарифа посетителя идёт сквозь всю цепочку** — браузер → хаб →
  исполнитель → хаб — в заголовке `X-AIMarket-Sandbox-Visitor`. Хаб считает обновляемый
  остаток на посетителя, поэтому пробрасывать нужно именно его идентификатор, а не сервиса:
  иначе все делят одну исчерпанную корзину вместо собственных остатков.
* **Хоп, которому нужны деньги, падает как этот хоп.** `402` — требуется оплата, `429` —
  остаток израсходован; с видимой причиной и никогда молча. Смета при этом всё равно
  говорит, сколько бы это стоило.
* **В bill of materials записан `payer` по каждому хопу** — `local`, `trial`, `channel` или
  `unpaid`, — так что бесплатный прогон никогда не становится подписанным доказательством
  покупки.

За пределами бесплатного тарифа хоп рассчитывается по платёжному каналу, которым владеет
вызывающий, и в записи указан этот канал.

## Как прочитать прогон обратно

Исполнитель подписывает bill of materials на каждый прогон и сохраняет его. До появления этих
маршрутов прочитать его было нечем: хоповая атрибуция вины — свидетельство, на котором стоит спор и
любое последующее списание (slashing) — была видна только тому, кто сделал исходный POST.

| Маршрут | Что возвращает |
|---------|----------------|
| `GET /ai-market/pipelines?limit=N` | Недавние прогоны как **вычищенную проекцию**: стоимость, хопы, статус по хопам, вина. |
| `GET /ai-market/pipelines/{trace_id}` | **Подписанный** bill of materials, дословно. |

Разделение сделано намеренно. Подпись покрывает объект как он записан, поэтому фильтрация ответа по
идентификатору выдала бы непроверяемое. Перечисление — обратная задача: публичная лента прогонов
раскрыла бы, какой платёжный канал что оплатил, и одноразовые номера квитанций по хопам, которые
служат ключами поиска публичных квитанций с суммами. Поэтому листинг убирает `channel_id` и
`receipt_nonce`, а каждая строка называет путь к своему подписанному оригиналу.

### Вина

Отказ конвейера — вина отказавшего хопа, а не всего графа. Bill of materials называет виновный хоп и
явно снимает вину с предшествующих хопов, сделавших свою работу, чтобы спор был направлен только на
ответственного провайдера:

```json
{
  "policy": "hop-level",
  "at_fault": {"id": "v", "capability_id": "metis.verify@v1", "status_code": 500},
  "not_at_fault": ["s"],
  "not_executed": ["d"]
}
```

## Как отправить граф

Чертёж превращается в тело запроса исполнителя. Едут только узлы-возможности: триггеры и выводы —
это то, как человек читает канвас, а не хопы, за которые кому-то выставляют счёт:

```json
{
  "nodes": [
    {"id": "s", "product_id": "prod-mcp", "capability_id": "web.search@v1",
     "input": {"query": "a claim"}, "depends_on": []},
    {"id": "v", "product_id": "prod-metis", "capability_id": "metis.verify@v1",
     "input": {"claim": "a claim"}, "depends_on": ["s"], "input_from": "s"}
  ]
}
```

```bash
curl -s -X POST https://magic-ai-factory.com/ai-market/pipelines \
  -H 'content-type: application/json' --data @blueprint.json
```

Ответ несёт `trace_id`, подписанный `bill_of_materials` и `final_result`.

Ядро специально без зависимостей и без DOM: ему обслуживать и страницу студии, и любую другую
поверхность, которой нужно посчитать или преобразовать чертёж, поэтому оно не может тащить с собой
взгляды конкретного UI-фреймворка.

```bash
cd hephaestus && npm install && npm run check    # типы + 57 тестов
```

## Ограничения, которые стоит назвать прямо

* Смета — не оферта. Цены берутся из подписанного манифеста в момент чтения, и провайдер может
  изменить их до прогона.
* `reputation_basis: measured` означает, что возможность вызывали через *этот* хаб в течение 30
  дней. Это свидетельство, а не гарантия.
* Подписанный bill of materials доказывает то, что записал исполнитель. Он не доказывает
  правильность результата — для этого существует уровень верификации.
