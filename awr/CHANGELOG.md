# Changelog

All notable changes to **AWR — Agent Work Receipt**. This file tracks the *specification* and
the artefacts that make it checkable; each implementation's own history lives in its
directory.

The version in [`VERSION`](VERSION) is the specification version, and it is also the value
`awrVersion` must carry (SPEC.md §3.1). Reason codes are **stable across versions**: a code is
never re-used for a different meaning, and a retired code is marked retired, never recycled
(§11.1).

This project uses [Semantic Versioning](https://semver.org/) with the wire format as the
public API. A **major** bump means a document conforming to the old version is not a valid
document under the new one — which is why `awrVersion` is inside the signed bytes, so an
intermediary cannot re-interpret a document under a different version's rules (§3.1).

## Unreleased — 2026-08-02 (security fixes; W3C VC interoperability)

`VERSION` stays `2.0.0` and so does `awrVersion`. **Nothing here changes what an AWR/2 issuer
signs**: the hashed proof configuration, `hashData` and the signature over it are all as
before. One change (§6.2 step 9) adds a member to the *emitted* proof, which leaves standalone
signatures valid but does move the document's own `digestSRI` — see the migration note below.
The rest change which rule set a verifier applies to a document, what it is allowed to say
about an AWR/1 one, and which RFC 8032 verification variant it uses, so a document that was
valid before and is rejected now was never anything but a forgery.

### Fixed — authentication bypass through the §12 legacy path

All three implementations selected the AWR/1 rule set on `proof.type ==
"Ed25519Signature2018"` and nothing else, and then took the verification key from the
document's own `issuer` object. AWR/1 signs neither of those, so **anyone could mint a
document that all three reported `valid: true`** — `documentType: WorkReceipt`,
`awrVersion: "2.0.0"`, exit 0, unchanged under `--profile L0` — while naming a victim's
`did:key` in `issuer.id`. It needed no secret: a target's DID is public.

The spec now says how a verifier chooses its rule set, and what an AWR/1 verification is
allowed to conclude.

- **§12.3, the version gate.** A closed list of five AWR/2 signals (`awrVersion`, either
  AWR/2 `@context` URI, a `DataIntegrityProof`, `validFrom`/`validUntil`,
  `credentialSubject.settlement`). A document carrying any of them **is** AWR/2 whatever
  its `proof.type` says; carrying one *and* an AWR/1 proof is `AWR-LEGACY-003`, verified
  under neither rule set, with no fallback to the other. Position in a `proof` array is
  irrelevant — two implementations read `proof[0]` and one read any element, so the sender
  chose the rules by ordering the array. Content heuristics are forbidden outright: the
  browser verifier had one that routed documents to the legacy path with no legacy proof
  present. `credentialSubject.parents` is deliberately *not* a signal, because Appendix D
  records that AWR/1 carried `parents` too.
- **§12.4, the unsigned issuer.** An AWR/1 result names a **key**, never an issuer. The
  §11.1 result carries `legacy.keySource`, `legacy.issuerAttested` (always `false`),
  `legacy.verifiedKey` and `legacy.unsignedFields`, and any issuer member is `null` on this
  path. A key taken from the document is `AWR-LEGACY-004` (warning): the signature then
  shows only that the file is internally consistent. Two disagreeing statements about the
  signer — an `issuer.id` `did:key`, with or without the §5.3 `#`-fragment, that is not the
  key used — are `AWR-KEY-003` (error); the fragment form is where the one implementation
  that *did* cross-check lost the check.
- **`--expected-key`** (§12.4, §17) supplies the key out of band and is then the only key
  tried, with no fallback to the document's. **`--no-legacy`** (§12.3, §17) declines §12
  entirely (`AWR-LEGACY-005`); support for AWR/1 has always been OPTIONAL and no
  implementation offered a way to refuse it.

New codes: `AWR-LEGACY-003` (error), `AWR-LEGACY-004` (warning), `AWR-LEGACY-005` (error).
`AWR-KEY-003`'s registry entry gains the AWR/1 case. `verifiedProof` is `null` for
`AWR-LEGACY-003`/`005` (§11.1): the document was verified under no rule set at all.

Nine vectors, generated by `awr/vectors/generate.py` (115 total, 345/345 across the three
implementations): the exact bypass, each AWR/2 signal on its own, a mixed `proof` array in
both orders, the two pure-AWR/1 key-disagreement forgeries, and a control whose two key
statements agree and which must still verify.

### Fixed — AWR/2 documents did not verify under an off-the-shelf `eddsa-jcs-2022` library

§1 claimed "any conformant W3C VC library can check an AWR document" and it was not true.
AWR copied the document's `@context` into the proof configuration it *hashed* (§6.2 step 1)
but never *emitted* `proof.@context`. A real off-the-shelf verifier rebuilds the proof
configuration from the serialized proof and adds nothing to it, so it hashed a different
configuration and reported a signature failure over correct bytes: `@digitalbazaar/vc`
7.3.0 + `@digitalbazaar/data-integrity` 2.5.0 + `@digitalbazaar/eddsa-jcs-2022-cryptosuite`
1.0.0 returned `Invalid signature.` on `awr/vectors/proof/worked-example-secured.json`.

**§6.2 gains step 9**: the emitted proof carries the document's `@context`. This is the one
change in this release that alters the bytes an AWR/2 issuer produces — and it does **not**
alter the bytes it signs. `hashData` is unchanged and so is the signature over it: the worked
example still carries `z2R1VSDk8Bub…`, and that same `proofValue` now verifies under the
library above. §6.1 lists `@context` as a proof member, §6.3 step 4 requires a verifier to
keep accepting a proof that omits it, and `awr/conformance/run.py` now asserts that an
implementation's `issue` emits it, so a regression is measured rather than discovered by a
third party.

**Migration is not uniformly free.** A standalone document is repaired by inserting the
member; its signature still verifies and no key is needed. But §3.2 digest references hash
the referenced **secured** document, so repairing a document changes its `digestSRI` and
every document that points at it — chain parents, `verifiedWork`, a blame `chain` — must be
re-issued by its own issuer, leaves first. Regenerating `awr/vectors/` shows the split
exactly: 62 files whose every `proofValue` is byte-identical to the previous release, and 30
chain/verdict/blame/bundle files that were re-signed because a digest they commit to moved.
§6.2 now spells this out.

### Fixed — §6.2 step 7 named no RFC 8032 verification variant

"Pure EdDSA per RFC 8032" is not one rule. RFC 8032 §5.1.7 permits both the cofactored and
the cofactorless group equation and requires rejecting neither small-order public keys nor
non-canonical point encodings, so two conformant implementations can disagree about the same
64 bytes — and the two shipped AWR implementations did: one used strict verification, the
other its language's permissive default.

**New §6.3.1** pins one rule, as four requirements: canonical encodings of `A` and `R`
(y < p, rejected rather than reduced), canonical `S` (0 ≤ S < L), no small-order `A` or `R`,
and the cofactorless equation `[S]B = R + [k]A'`. The small-order clause is the load-bearing
one: with `A` = the identity element, `R` = the base point and `S` = 1, both group equations
hold for every message with no private key in existence, and because the eight small-order
points encode to eight distinct `did:key` values, a keyless party could satisfy §10.3's "two
verdicts from distinct issuers" and be handed the `L2` "Accountable" label.

## 2.0.0 — 2026-08-01 (draft standard)

The first version specified precisely enough to implement twice. AWR/1 was a working file
format with one implementation; AWR/2 is a specification with three, a reason-code registry,
106 vectors that carry their own expected outcomes, and a conformance suite that drives any
implementation through a documented CLI.

### Breaking changes against AWR/1

Every item below is a change an AWR/1 document does not survive. AWR/1 documents remain
*verifiable* under the §12 legacy annex, but they are not AWR/2 documents and must not be
re-signed as such (§12.2).

| Change | Why |
|---|---|
| **Whole-document signing** (was: `credentialSubject` only) | `id`, `issuer` and `type` were outside the signature while `parents` referenced ids, so an intermediary could rename a valid receipt and re-point a chain without breaking any signature (§13.1) |
| **RFC 8785 JCS, exactly** (was: a JCS-labelled variant with NFC normalization, code-point key sort, and 10-decimal float truncation) | Two implementations of the same format disagreed on the bytes for any integer field. Key order is over **UTF-16 code units**, not code points, and no Unicode normalization is applied (§4.1) |
| **Integers only in signed documents; every non-count is a decimal string** (§4.3) | Removes the int/float divergence class instead of arbitrating it. The check is **lexical**: `2340.0` is `AWR-CANON-001` even though its value is a whole number, because an implementation that decides after parsing accepts a document no conformant issuer produced and canonicalizes it to bytes its issuer never signed. `2340` vs `2340.0` is the exact divergence that split AWR/1 into two incompatible dialects |
| **`eddsa-jcs-2022` + `DataIntegrityProof`** (was: `Ed25519Signature2018`, base64 `proofValue`) | Deprecated suite. The current one is a W3C Recommendation with off-the-shelf verifiers; `proofValue` is now multibase base58btc of exactly 64 bytes, and the legacy base64 form is rejected (§6.1) |
| **Real `did:key` derivation** (was: `did:key:` + the first 32 characters of a base64 public key) | The legacy value was not a valid DID and named a different key than the document embedded. `AWR-KEY-002` (malformed) and `AWR-KEY-004` (well-formed, wrong key type) are now reported distinctly, and never both (§5.1) |
| **`parents` as digest references** (was: identifier strings) | Content-addressed edges: an edge commits to the parent's exact bytes *and its signature*, so a chain cannot be re-pointed while remaining valid (§8.1) |
| **`VerificationVerdict` and `BlameAttestation` as separate signed documents** | The verifier and the blame attributor get their own `did:key`, and therefore accountability. A judge with no identity is a rubber stamp |
| **Attestations are explicitly opaque**, `AWR-ENV-001` (warning) when present and unverified | The legacy verifier checked a TEE attestation's inner signature with the *receipt issuer's* key. That is worse than no check: it proves only that the party making the claim also wrote it down, while presenting as hardware evidence (§7.3) |
| **Age is a warning, not invalidity** (§11.3) | The legacy verifier hard-failed documents older than 90 days. A receipt from two years ago is exactly as cryptographically sound as one from today, and an audit is the main reason old receipts are read |
| **Reason-code registry; all determinable errors reported** | Independent implementation is not feasible against a boolean (§11.1) |

### Added

- **`SPEC.md`** — the normative specification: document model (§3), canonicalization (§4),
  issuer identity (§5), proof (§6), optional attestations (§7), work chains (§8), bundles
  (§9), the L0/L1/L2 profile ladder (§10), the result shape and reason-code registry (§11),
  the AWR/1 legacy annex (§12), security (§13) and privacy (§14) considerations, mappings to
  neighbouring standards (§16), and the **§17 CLI contract**.
- **Three assurance levels** (§10). L0 requires an Ed25519 keypair and nothing else — no
  payment, no blockchain, no account, no network. L1 requires a verdict from a *different*
  issuer. L2 requires two distinct verdict issuers plus an accountability binding, checked
  for presence and signature only: a verifier **must not** contact a chain (`AWR-L2-001`).
- **`vectors/`** — 106 vectors and `index.json`, which is the arbiter rather than
  documentation: every entry carries its expected outcome, the exact reason codes that must
  be reported, and a mandatory `why` naming the attack or divergence it exists to catch. All
  signing seeds are published RFC 8032 §7.1 test vectors, so the set created no secret.
- **`vectors/check_vectors.py`** — holds the manifest to its own contract: §11.2 code
  coverage, generator determinism (regenerate and diff), no orphan vectors, and the two
  properties no CLI can show.
- **`vectors/interop.sh`** — the reverse direction: every implementation *issues*, all of
  them verify, and the issuers' bytes are compared. Handing fixed bytes to a verifier cannot
  catch an issuer that writes bytes nobody else accepts.
- **`conformance/`** — `run.py`, which drives **any** implementation purely through the §17
  CLI and records a per-vector, per-implementation matrix; `implementations.json`, the
  registry; `results.json` and `badge.json`, generated. Standard library only.
- **Three implementations** — the Python reference, an independent Rust build written from
  `SPEC.md` without reading the reference source, and the browser verifier behind a §17
  adapter so the code a stranger's browser runs is the code the matrix measures. As of this
  release all three pass 106/106.
- **`schemas/`** — JSON Schema for the three documents plus bundles, explicitly
  non-normative: where a schema and `SPEC.md` disagree, the schema is the bug (Appendix B).
- **`adoption/`** — the adoption metric, the MCP trust-label profile, outreach drafts.

### Fixed during 2.0.0, as a result of the second and third implementations

Each of these was a live divergence between conformant-looking implementations that the
specification did not settle. They are recorded because "we clarified the spec" is not a
useful changelog entry without the divergence that forced it.

- **§6.3 — which code to report when the signature could not be checked.** One
  implementation called an underivable public key a signature failure and another did not,
  making their outputs incomparable. Settled: the step that prevented the check reports its
  own code and `AWR-PROOF-006` is **not** additionally reported. The registry needs no "could
  not check" code because the blocking step always has a more specific one.
- **§11.1 `verifiedProof`.** Two conformant verifiers reported `0` and `null` for the same
  valid document. It is now REQUIRED whenever §6.3 step 6 succeeded, and a **function of the
  codes reported** in both directions. `documentType: null` is explicitly *not* a signal that
  no proof was checked.
- **§11.1 `awrVersion` and `documentType`.** One implementation reported its own version,
  another the invented string `"1"`, a third a document type name that appears in no document.
  Both members now report what the **document** carries, and both are `null` whenever any
  `AWR-CANON-*` code is reported, since a document with no canonical form has no confirmed
  content to quote back.
- **§11.1 `chain`.** One implementation counted a verdict's `verifiedWork` and a blame's
  reachability walk as chain edges, so a standalone verdict claimed one unresolved hop. The
  member now counts §8.1 `parents` edges and nothing else; a malformed edge counts in neither
  total.
- **§8.2 — locating a parent, and why cycle detection must walk past a failed edge.** A
  digest cycle would be a SHA-256 fixed point, so `AWR-CHAIN-004` is unreachable for a
  resolver that stops at the first digest mismatch. Cycle detection now keys on document `id`
  and a cyclic bundle reports `AWR-CHAIN-003` **and** `AWR-CHAIN-004`.
- **§9 — an unsupported `awrBundle` version is not partially interpreted.** Two
  implementations verified the contents of an `awrBundle: "1.0"` container and reported the
  enclosed receipt's type and proof index; a third refused. All three reported
  `AWR-BUNDLE-001`, so no code set revealed the disagreement. Now fail-closed, matching the
  gate §3.1 puts on `awrVersion`.
- **§10.4 — three cases the profile rules left implicit.** The profile of an invalid document
  is `null`; the profile of a non-`WorkReceipt` is `null`; and `AWR-PROFILE-*` codes are
  reported only for a profile the caller requested, since they carry severity `error` and
  would otherwise make every plain L0 receipt invalid.
- **§12.1 — the AWR/1 pipe-delimited rendering, written out.** The earlier text said only "a
  pipe-delimited rendering of `credentialSubject`", from which two implementations produced
  different bytes and neither could read the other's receipts. Leaf traversal, path sorting,
  the empty-container rule and per-dialect number rendering are now specified.
- **§17 — the CLI contract, and `--subject` by name.** A harness that has to guess a flag
  cannot drive two implementations from one manifest, so the flag names are normative.

### Known gaps

- **`AWR-CANON-006` is unreachable from any input.** It reports that the implementation's own
  canonicalizer is lossy, which is a property of the implementation, not of a document.
  `check_vectors.py` proves it fires by pointing the reference self-check at a deliberately
  NFC-applying canonicalizer; the CLI-driven suite cannot.
- **`AWR-BUNDLE-001` has two causes and only one is exercised** — an unsupported `awrBundle`
  version, but not a non-object entry inside an otherwise supported bundle. A vector for the
  second must split the `verifiedProof` invariant rather than relax it.
- **`issue` is under-specified for determinism.** §17 fixes the key-file form but says nothing
  about how an issuer obtains `id` and `validFrom`, so both issuing implementations invent a
  UUID and read the clock. Byte-for-byte comparison of two issuers therefore needs `--id` and
  `--now`, which §17 does not define; `interop.sh` relies on them as an extension.
- **No revocation, by construction** (§13.6). A compromised key cannot be un-said, only
  superseded (§5.4).
- **TEE and ZK attestations are carried but never verified** (§7.3). Verifying one needs a
  platform certificate chain, which is a network- and vendor-dependent operation and therefore
  outside the offline-verifiable core. `AWR-ENV-001` is the honest outcome.

## 1.x — AWR/1 (superseded, verification only)

Not released as a specification: a format defined by its single implementation. Documents
carry `Ed25519Signature2018`, a base64 `proofValue`, and a signature over a pipe-delimited
rendering of `credentialSubject` only, in one of **two mutually incompatible dialects** —
integer-preserving and float-coercing — because the reference issuer was written in a
language that distinguishes integers from floats and the reference verifier in one that does
not.

An AWR/2 implementation **may** verify AWR/1 documents; if it does it must report
`AWR-LEGACY-001` on every one, must treat `id`, `type` and `issuer` as **unsigned**, must try
both dialects, and must never issue AWR/1 (§12). See Appendix D of `SPEC.md` for the full
comparison.
